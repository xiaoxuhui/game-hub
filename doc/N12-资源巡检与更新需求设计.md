# N12 资源巡检与更新：需求、设计、验收

- 日期：2026-10-12（Asia/Shanghai）
- 授权：用户要求再检查游戏资源，有更新就更新；沿用原仓只读、独立构建、阶段提交后独立审阅、发布后清理及真机补验授权。
- 本轮更新资源，不重新发行 APK；PWA/iPad 适配属于另外的需求。

## 需求

U01 六个原游戏仓库、七名资源消费者分别核查正式 Release 与默认分支。仅文档/测试差异不更新 ZIP；固定来源领先主分支不回退。

U02 本次是维护者手动审阅并发布固定源码修订；上游仍未提升正式版本，不能声称发布了新上游版本。大厅的 contentCode 与资源目录 sequence 递增，让同版本号的兼容修订仍能被已发行 APK 检出。

U03 有存档迁移、旧版无法读取的新格式或新原生能力需求，不直接沿既有兼容合同发行。独立审阅判断是否可继续；不为凑齐更新而放宽协议。

U04 ZIP 先上传核验、签名目录最后公开；保留历史 ID/ZIP/目录和固定标签。私钥在本机 DPAPI 内存解密并 stdin 签署，不能进入仓库、Actions、日志或明文文件。失败与未知结果先只读对账。

## 设计

1. 康威只改资源来源锁/编号锁和脚本白名单，sources.lock.json 的内置 APK 基线不动。
2. 两动态适配按固定上游完整 SHA 在本轮独立检出运行已有 stage-upstreams 工具，逐文件 Git blob 对齐，Lambda 还要求 tracked dist 与实际构建相同；生成来源证明和 MIT 原文，再提交大厅适配资源，固定 dynamic-sources 锁到对应适配提交。
3. 发布器只增加本轮 n12 的严格任务范围，沿用原来的干净且已推送来源门禁、生产公钥、完整历史验签、累积资产校验、原目录摘要和下一序号约束，不削弱检查。
4. 生产候选重复独立构建并完整比字节；已有未改游戏 ZIP 应与线上摘要相同，不因改大厅提交引起无意义重下载。
5. 浏览器同 origin 加载旧已发行资源→真实保存→新资源，验证旧记录和操作；手机/桌面尺寸分别检查三游戏。正式大厅 0.4.1 的 Android 生产端点/公钥验收单独进行，测试 APK 不代替正式宿主。原 APK 字节/版本/证书保持。

## 验收用例

- T01 查询六源和七基线；错误不会标最新，未正式发布与同版修订区分。
- T02 固定源码、白名单、MIT 与入口/脚本依赖闭包校验；来源证明与固定 Git blob 相同。
- T03 Node 全套回归和受影响上游领域测试；同一大厅干净提交两次生成候选全部字节一致。
- T04 康威旧自定义记录/逻辑函数保留，批量导入/导出及确认删除可用，取消不删除，无全局清存档。
- T05 阿贝尔旧模式/关卡/间隔保存保留，整数输入范围与空输入可再次使用；Lambda旧检查点/库/工作区保留、手动归约及视口操作可用。
- T06 EML旧读写器对新增格式兼容审阅；若违反已批准合同，本轮不更改其资源锁，阻断原因有实际代码/试验依据。
- T07 发布前严格绑定旧目录与完整历史、新序号、干净推送来源；发布后匿名下载验签及全部引用ZIP摘要，正式0.4.1实际安装/打开/存档/离线恢复。
- T08 清理唯一根 D:\soft\.ci-tmp\game-hub-n12 前归档必要恢复/审阅/测试/发布证据；原仓 SHA/完整状态再次相等。
