# 游戏合集 APK：需求与测试用例

> 本文件保留 v0.2.0 及更早实施背景；新版启动提醒与子游戏资源更新见 [v0.3.0 需求规划](需求与测试用例-v0.3.0.md)。旧版“仅手动检查”“不做热更新”等边界在新版规划范围内被替代，尚未变成已实现功能。

- 状态：已批准实施；U01–U15 尚待逐项验证
- 日期：2026-09-30
- 项目目录：`D:\soft\game-hub`；已建立独立 Git 仓库和私有远端

## 1. 背景与目标

目前 `D:\soft` 下的康威生命游戏、EML 计算台、光学游戏、图灵机实验台各自产出 Android APK。用户希望只安装一个 APK，通过首页选择并游玩四个项目。四个原仓库继续独立开发；合集项目只读取锁定版本的网页源码或构建产物，任何构建及发布流程都不得回写原仓库。

本项目交付的是一个新的 Android 应用。其版本、包名和签名独立于四个现有 APK。

## 2. 范围与来源

| 游戏 | 源仓库 | 当前网页形态 | 合集入口 |
|---|---|---|---|
| 康威生命游戏 | `conway-life-game` | 静态多文件 | `index.html` |
| EML 计算台 | `EML` | 构建后的单文件 HTML | `eml-workbench.html` |
| 光学游戏 | `light_game` | 静态多文件 | `index.html` |
| 图灵机实验台 | `turing-machine-simulator` | Vite 多页面构建产物 | `index.html`；游戏内可进入 `campaign.html` |

首版包含上述四项。光学游戏与 EML 虽不都是传统意义的“游戏”，首页统一称为“应用”或“项目”，具体名称仍使用各自产品名称。

## 3. 用户流程

1. 安装并打开合集 APK，看到四个项目的名称、简短说明和进入按钮。
2. 点选项目后进入其原有网页界面，核心玩法和页面结构保持原样。
3. 在项目内使用系统返回键时，先处理该项目的页面历史；回到入口时返回合集首页。
4. 从首页进入另一项目；各项目的本地进度、草稿和设置在合集 APK 内持续保留。
5. 断网后仍可打开首页并使用全部四个项目。

## 4. 功能需求

### R01 统一安装与入口

- 只发布一个合集 APK，安装后在系统桌面显示一个应用图标。
- 首页列出且能打开全部四个项目；项目入口不能依赖远程网页。
- 首页显示合集版本及每个项目实际打入包内的版本或提交标识，便于排查问题。

### R02 原项目功能可用

- 网页资源从 APK 内读取。支持各项目现有的脚本、样式、图片及图灵机实验台的 Worker 和关卡页。
- 保留文件导入入口，并使现有导出功能在 Android WebView 中可用。
- 不要求在原游戏仓库中加入“返回大厅”按钮；导航由合集 Android 外壳承担。
- 手机竖屏、平板横屏及系统栏变化时页面可操作；具体触摸交互以原游戏已有能力为准。

### R03 数据与兼容

- 同一项目在合集 APK 的多次启动、项目切换及覆盖升级后保留本地数据。
- 首版不自动读取四个旧 APK 的内部存档。Android 应用沙箱使新包不能直接访问它们的私有数据。
- 已有导出和导入路径的项目，可由用户自行迁移；具体可迁移范围在实施时逐项核对并写入使用说明。
- 四个项目共享合集 APK 的 WebView 数据空间时，必须验证存储键互不冲突，也不能让一个项目清空其它项目的数据。

### R04 源仓库只读

- 合集仓库记录四个来源的仓库地址、固定 Git 提交、构建命令、产物入口和校验信息。
- 构建在隔离的临时工作目录中检出来源，生成资源后复制进合集 APK；不得在四个原仓库中写入或提交文件。
- 升级某一项目时，只调整合集仓库的版本锁定和必要的合集适配代码，重新构建并验证四个项目。
- 资源缺失、构建失败或锁定版本不匹配时停止出包，不发布部分可用的 APK。

### R05 安装与升级

- 合集 APK 使用独立且固定的 `applicationId` 与签名；`versionCode` 在每次发布时严格递增。
- 首版可与四个原 APK 并存。安装合集不会覆盖、卸载或改变旧应用。
- 后续合集版本应能直接覆盖安装前一版，并保留合集内存档。

## 5. 非功能要求

- 离线运行；运行时不依赖 GitHub、GitHub Pages 或本地服务。
- 默认不申请网络、存储等额外 Android 权限；如后续需求使权限不可避免，须单独评审。
- 仅打入运行所需资源，不把测试、源码管理元数据和构建工具打进 APK。
- 首页与切换操作应有可识别的加载和失败状态，不能静默白屏。
- 构建结果可追溯到四个源提交及合集提交；发布包附带文件摘要。

## 7. 暂不包含

- 不合并四个游戏的 Git 历史、源码目录或发布流程。
- 不把各游戏的独立 APK 改造成合集的插件，也不要求用户先安装它们。
- 不自动迁移旧 APK 的私有存档。
- 不做在线下载游戏、热更新、账号同步、广告或跨游戏成就。
- 不改变四个游戏自身的规则、关卡和网页界面。

## 8. 实施前待确认

1. 合集的正式名称、桌面图标与 `applicationId`。
2. 首版是否需要提供旧 APK 存档的逐项目手动迁移说明；不能承诺所有项目都支持完整迁移。
3. 发布范围：仅个人安装，还是同时提供 GitHub Release 下载。该决定影响签名及分发安排。
4. 首版支持设备的最低 Android 版本，暂按现有四个外壳共同采用的 `minSdk 24` 设计。

这些事项不妨碍需求与技术方案先行，但发布前必须定稿。

## 9. 2026-09-30 实施决定

用户已授权按阶段开发、提交并推送至新建的私有远端仓库；每个阶段提交后须从独立审核视角审阅、批改并存档，然后才能进入下一阶段。开发期间至少每 10 分钟汇报一次带勾选框的进度。当前范围止于实现、构建与验证，暂不公开仓库、部署、打标签或发布 APK。

为让工程能独立推进，首版暂用显示名“游戏大厅”、`applicationId` 为 `com.xiaoxuhui.gamehub`、`minSdk 24`，图标采用可复现的几何图案。正式分发前可在未发布的合集工程中调整名称与图标；包名和签名必须在首次对外分发前锁定。旧 APK 存档仅提供已有导入/导出能力所支持的手动迁移说明。

## 10. 大厅与手动更新增量需求（2026-09-30）

- R06：手机常见竖屏尺寸下四个项目以 2×2 图标网格在首屏可见。使用四个固定来源的原 APK 图标；每格保留名称和紧凑的内置版本/提交短标识，整格可点击。移除重复的介绍文字和四个大按钮；小屏或大字体时允许滚动，不能裁切入口。
- R07：大厅提供“检查更新”入口，仅由用户手动触发联网。查询本仓库**公开的最新正式 GitHub Release**；仓库私有或没有 Release 时清楚提示暂无公开版本，不在 APK 中保存 GitHub 凭据。四个内置游戏继续离线运行。
- R08：若公开 Release 版本高于当前合集版本，用户确认后下载固定名称的 APK。下载前校验 Release 元数据中的 SHA-256、文件名、大小和 GitHub URL；下载后核对摘要、包名和递增的 `versionCode`，再交给 Android 系统安装界面，由用户完成授权与安装。失败或取消不覆盖现有应用及存档。不做静默安装、后台自动提醒或游戏网页热更新。
- R09：正式发布前固定签名材料并验证两版覆盖安装；当前随机调试签名 APK 不承诺能直接覆盖为正式版，现有测试用户需先导出可迁移数据。
