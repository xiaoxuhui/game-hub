## 1. 设计目标与边界

合集仓库负责首页、Android WebView 外壳、源版本锁定、资源组装、构建验证和合集 APK 发布。四个游戏仓库继续负责自己的玩法及网页产物。合集构建只读取指定提交，不把生成资源写回来源仓库。

```
四个游戏仓库的固定提交
          │ 只读检出、各自构建
          ▼
   合集仓库的资源组装脚本 ──→ APK assets/games/<id>/
          │                         │
          └── 版本清单 ──→ Android 大厅 ──→ WebView 打开项目
```

已在 `D:\soft\game-hub` 建立第五个 Git 仓库与私有远端。四个来源在独立目录构建，CI 已生成调试 APK；四个原游戏仓库保持固定提交和洁净工作树。当前尚未正式发布。

## 2. 来源锁定与构建

以一份机器可读清单锁定四个项目，示意字段：`id`、`displayName`、`repository`、`revision`（完整 Git SHA）、`buildKind`、`entryPage`、`assetManifest`。构建脚本拒绝浮动分支名作为正式版本。生成的 `bundle-manifest.json` 记录合集提交、四个源提交、网页版本及各资源摘要。

| 来源 | 读取和打包策略 | 需要重点验证 |
|---|---|---|
| 康威生命游戏 | 从固定提交复制 `index.html` 及运行时脚本、样式 | 页面引用的全部本地文件已列入资源清单 |
| EML 计算台 | 运行固定源中的 `node scripts/build.mjs`，复制 `dist/eml-workbench.html` | 单文件输出与源提交一致 |
| 光学游戏 | 从固定提交复制 `index.html` 及其列举的脚本、样式 | 不把本地服务器和 Android 同步脚本打进包 |
| 图灵机实验台 | 安装锁定依赖，运行类型检查及 `build:android`，复制完整 `dist` | Vite 构建使用相对 `base`，关卡页和 Worker 可加载 |

开发时允许从本机路径只读获取来源；正式构建以 Git SHA 检出到独立临时目录，避免“本机碰巧有未提交文件”影响结果。任何构建脚本都不得执行 `git push`、向来源工作树写入或自动更新四个仓库。缓存和临时目录放在合集仓库或系统临时目录，并排除版本控制。

## 3. APK 资源布局

```text
assets/
  games/
    conway/index.html ...
    eml/eml-workbench.html
    light/index.html ...
    turing/index.html
    turing/campaign.html ...
  bundle-manifest.json
```

WebView 通过 `WebViewAssetLoader` 把这些文件映射到保留 HTTPS 域名 `appassets.androidplatform.net` 下的 `/assets/games/<id>/`。所有页面内资源必须采用可在该子目录下解析的相对路径。拦截请求只允许已登记的内置资源路径；外部链接交给系统浏览器。文件找不到时显示明确的失败页，并在开发构建中记录具体路径。同一 origin 的项目可以读取其它项目的只读包内资源，路径白名单只限制未登记资源，不构成项目间安全隔离。

Android 官方说明 `WebViewAssetLoader` 的 HTTPS 地址遵循同源策略，建议使用其保留域名或自己拥有的域名。先前讨论中提出的四个自造 `.local` 域名尚无所有权与兼容性依据，不作为首版设计。参考：[WebViewAssetLoader 官方文档](https://developer.android.com/reference/androidx/webkit/WebViewAssetLoader.html)。

## 4. 界面与导航

- 原生 Android 大厅显示四张项目卡片、版本信息和一个进入按钮。首页无需联网。
- 游戏容器每次进入创建该项目的 WebView；离开时保存应由网页自身持久化的数据，并销毁当前 WebView。新项目获得新的页面运行环境。
- 游戏内部的网页历史优先处理系统返回键；到达项目入口页时返回大厅。首页返回键退出应用。
- 按设备安全区域调整 WebView 边距，并支持现有外壳使用的文件选择器、外部链接处理和页面恢复策略。
- WebView 的页面历史不得穿越到上一个游戏；大厅与游戏的状态由 Android 外壳管理。

## 5. 存储与迁移

不同资源路径仍属于同一个 HTTPS origin，因此合集内四个项目的 `localStorage` 是共享的。当前源码中的主要键分别是：

| 项目 | 当前已见存储键 |
|---|---|
| 康威生命游戏 | `conway-life-game.custom-patterns.v1`、`conway-life-game.logic-functions.v1` |
| EML 计算台 | `eml_workbench_v2` |
| 光学游戏 | `light-game/save` |
| 图灵机实验台 | `turing-machine-simulator.project.v1`、`turing-machine-simulator.campaign.v1` |

首版采用现有互不相同的键，构建检查扫描存储访问和清空行为，设备测试覆盖一个项目重置后其它项目的数据。此方案实现了已知数据的互不覆盖，但不是浏览器级的强隔离；后续如需强隔离，应使用自己控制的不同 HTTPS 域名并单独验证资源拦截、导航与 Android WebView 兼容性。不得仅靠路径声称 origin 已隔离。

合集使用新的 `applicationId`，Android 沙箱中的旧 APK 私有数据无法被它直接读取。手动迁移只基于项目现有的导出与导入能力，不在首版中承诺自动迁移。合集首次打开时各项目默认新存档。

## 6. Android 原生能力

四个现有外壳的能力相近，但导出接口并不完全相同：康威、EML、图灵机使用各自的 Blob 下载拦截与 `saveFile` 桥；光学游戏从网页直接调用 `LightAndroid.saveFile`，且其返回值用于判断是否已受理。合集适配层需保留这些网页可见的接口名称与返回约定，同时共用一个经过文件名清理的 Android 保存实现。文件选择器共用一套实现。

应仅在加载受信任的包内网页时暴露原生桥，限制可导航域名和资源来源；外部网页不得留在持有桥的 WebView 中。Android 官方特别提醒 `addJavascriptInterface` 会暴露给页面中的 frame，须仅用于受信任内容。参考：[Android WebView 官方文档](https://developer.android.com/develop/ui/views/layout/webapps/webview)。

## 7. 包名、版本与签名

- 合集使用新的 `applicationId`，从而能与四个原 APK 并存。
- 合集 `versionName` 独立递增；四个内置项目各有自己的版本或源 SHA，展示在详情信息中。
- `versionCode` 严格递增；签名材料固定保管，发布前验证新旧 APK 的签名和覆盖升级能力。
- 首版发布前明确分发方式及签名策略。发布文件名、包内版本清单和 SHA-256 摘要需要对应同一构建。

## 8. 错误与边界处理

- 任一项目构建失败、资源缺失或 SHA 不匹配，整个合集构建失败。
- 首页在资源加载失败时显示项目名、可理解的错误说明和返回按钮。
- WebView 跳转非允许的内置路径时阻止在容器内打开；正常外链交给系统浏览器。
- 下载失败要明确提示，避免网页显示“已保存”而实际无文件。
- 合集包体积、冷启动与项目切换耗时在首个可运行原型上实测；不预设一定比四个 APK 之和更小。

## 9. 验证策略

1. 构建检查：清单 SHA 固定，四个源提交正确，来源工作树不变，资源引用完整，包内无开发工具。
2. Android 自动检查：包名、版本、签名配置、资源清单、四个入口及导航白名单。
3. 浏览器与 WebView 检查：四个核心流程、图灵机双入口及 Worker、存档、导入导出、外链与返回键。
4. 真实设备检查：断网、手机竖屏、平板横屏、旋转、杀进程重启、跨两个合集版本覆盖安装。
5. 每次升级单个来源时四个项目都做冒烟回归，并将源提交、构建命令、结果记入测试报告。

需求中的 U01–U15 是验收矩阵。只有实际执行并记录结果的项目可标为通过。

## 11. 架构评审修订的实施约束

1. 四个来源以 [`来源基线.md`](来源基线.md) 的完整 Git SHA 锁定。原仓库只读，实际构建在独立检出目录；无论本地分支或远端分支如何移动，都不改变首版来源。
2. 资源装入 `/assets/games/<id>/`，使用 `WebViewAssetLoader` 的 `appassets.androidplatform.net` 保留域名。资源路径按登记清单校验并拒绝逃逸；外链由系统浏览器承接，原生桥只随受信任页面创建。
3. 四项目共享一个 HTTPS origin；路径不同不构成存储隔离。对固定来源扫描存储键及清空操作，并在可用 Android 环境检验跨项目数据不被重置影响。
4. 导出桥兼容 `ConwayAndroid`、`EMLAndroid`、`LightAndroid`、`TuringAndroid` 的现有接口，其中光学游戏的 `saveFile` 返回值仍为布尔值。缺失或写入失败要有明确反馈。
5. 项目版本与 SHA 在大厅可见，完整资源摘要写入清单。任一来源构建失败时整个打包失败，不留下部分可分发的 APK。
6. 本轮默认名称“游戏大厅”、包名 `com.xiaoxuhui.gamehub`、`minSdk 24`；新远端保持私有，暂不发布或打标签。正式对外分发前再确定签名和发行策略。

## 12. 大厅改版与更新链路设计（2026-09-30）

大厅改用原生 2×2 等高网格。图标取四个固定来源提交中的 `android/icon-source/store-icon-512.png`，复制到合集 `res/drawable-nodpi`；不从会移动的分支取图。每格只显示图标、名称和紧凑版本/提交标识；整格承担打开动作。首页顶部保留合集版本，底部放手动检查更新。普通手机以无需滚动为目标，极小屏幕和系统大字体时允许滚动兜底。

更新检查与游戏 WebView 分离，走 Android 原生网络模块，WebView 仍仅允许已登记的包内资源。只请求 `https://api.github.com/repos/xiaoxuhui/game-hub/releases/latest`，不嵌入 token；私有期间无法对普通用户查询，公开发布后才有可用数据。Release 必须有固定名 `game-hub.apk` 和 GitHub 提供的 `sha256:` 摘要，且为非草稿、非预发布。发布标签使用 `vMAJOR.MINOR.PATCH`，用于检查页显示与初筛；资源下载 URL 根据 GitHub 返回的 asset ID 在 `api.github.com` 构造，不接受元数据中任意下载地址，重定向只允许 HTTPS GitHub 受控下载域名。下载后先核对摘要、包名、递增 `versionCode` 与 APK 签名证书是否等于**当前已安装的大厅证书**，再通过 `FileProvider` 交给系统安装界面；系统仍作最终签名与用户授权检查。此同证书校验只覆盖应用内升级，不能替首次安装证明发行身份；首次公开版的证书指纹、下载页与分发校验需在 P7 单独审计。限制下载大小和超时，先落入应用缓存并校验。仅点击检查时联网；没有任何自动查询或后台服务。

正式更新从首个稳定签名的公开版开始。CI 临时调试包的私钥不可复用，因此从当前调试包升级到正式签名包需要卸载重装；发布前在独立检出验证连续两版同签名覆盖及存档保留，并更新迁移说明。本轮可完成代码和模拟器验证，发布动作以最终审计为准。
