# N32 内置四款并入动态通道设计

> 状态：**仅为方案，未实施**（2026-11-23 肖工提出诉求，暂不执行）
> 适用：把 `conway` / `eml` / `light` / `turing` 从「内置通道专有四款」改成「动态通道普通条目」

## 1. 诉求与澄清

肖工原话的意思需要先钉清楚，因为很容易被误读成「下架」：

- **不是**删掉这四款，也不是停止更新——这四款还在玩，资源还要继续发；
- **是**取消「内置」这个身份：让它们和另外二十几款一样，由签名目录下发、由大厅按需安装，不再占用一套专门的通道、专门的 origin、专门的打包流程。

一句话：**换通道，不是下架。**

为什么不能真删，见第 4 节的三条硬约束。

## 2. 现状：内置与动态是两套独立机制

| 维度 | 内置（v1） | 动态（v2） |
|---|---|---|
| 签名目录 | `game-resources-v1/catalog.signed.json` | `game-resources-v2/catalog-expanded.signed.json` |
| id 从哪来 | APK 内 `assets/bundle-manifest.json`（构建时打包） | 运行时从签名目录拉 |
| 资源从哪来 | APK 内 `assets/games/<id>/` | Release 上的 ZIP → 解压到私有目录 |
| WebView origin | `appassets.androidplatform.net`（**四款共享根域**） | `<id>.appassets.androidplatform.net`（**各自独立子域**） |
| 存档契约 | `<id>-baseline-v1` | `<id>-dynamic-v1` |
| id 合法域 | 固定这四款 | `DynamicGamePolicy.validId` 明确**排除**这四款 |
| 首启可玩性 | 装完即玩，无需联网 | 需联网下载 |
| 更新闸门 | 人工（怕误加/误删 id 打垮存量 APK） | 自动 |

两端解析器互不复用：`DynamicGamePolicy` 的注释写得很直白——「accepting a dynamic game must never relax the four-game v1 parser」。

## 3. 需要改动的六处（实测位置）

| # | 位置 | 现状 | 改成 |
|---|---|---|---|
| 1 | `scripts/bundle.mjs:35,50` | `validateLock` 要求 `sources.length === 4` 且 id 集合严格等于四款；`assemble` 只处理这四条 | 放开为「可配置打包集合」，允许为空 |
| 2 | `MainActivity.kt:254,260` `loadBundleManifest` | 读 `assets/bundle-manifest.json`，`sources.length()!=4` 直接 `error`；`games` 与 `assetPaths` 全部由它初始化 | 内置集合为空时走「全部动态」分支，`assetPaths` 改由动态资源清单提供 |
| 3 | `ResourceStorePolicy.kt:11,19` | `initialIds` = 四款；`requireIds` 要求 `incoming == initialIds` | 删除 BUILTIN 枚举或让其退化为空集 |
| 4 | `DynamicGamePolicy.kt:9-10` | `validId` 显式排除四款 | 移除排除，四款按普通 id 规则校验 |
| 5 | `AssetAccessPolicy.kt:5-8` | 内置走根域，其余走 `<id>.<DOMAIN>` | 见 5.1：**建议保留这四款走根域** |
| 6 | `GameResourceStore.kt:80,268,280,339,343` | 多处 `active == "builtin"` 特判（不可卸载、恢复内置版本、契约判定） | 特判收敛或删除 |

这六处之外，`AssetAccessPolicy.pageAllowed` / `GameContentResolver` 的白名单都以「注册路径」为判据，本身不区分内置与动态，不需要动。

## 4. 三条硬约束（决定了「不能直接删」）

1. **`scripts/bundle.mjs:50`**——构建时硬校验四款 id 必须存在。APK 打包了它们的资源，这是首启离线可玩的前提。
2. **`ResourceStorePolicy.kt:19`**——`incoming == initialIds`。v1 目录必须**严格等于**这四款，少一个，存量老 APK 会整份拒绝目录，一个游戏都不显示。
3. **`requireIds` 的 `known.all { it in incoming }`**——本地已装的游戏必须都在新目录里。**目录只能加，不能删。**

第 3 条同样约束本方案：这四款一旦有玩家装着，它们在目录里的位置就必须一直保留，只是身份从 v1 换成 v2。

## 5. 三个真正的难点

### 5.1 存档迁移（最重，也最容易被低估）

内置四款跑在**共享根域** `appassets.androidplatform.net` 上——四款共用一个 localStorage，靠 `storage-isolation.js` 加 key 前缀隔离。动态款跑在 `<id>.appassets...` 独立子域上，天然隔离。

这意味着：**把一款从内置改成动态，等于换了 origin，浏览器存档直接归零。**玩家在 conway 里造的世界、eml 里的项目、light 里的关卡进度、turing 里的程序，全部消失。

而跨 origin 是无法在页面里直接读写的，迁移只能在 APK 侧做：宿主在根域上下文里 `evaluateJavascript` 读出 `<id>:*` 的键值，再注入到子域上下文；注入必须发生在游戏脚本首次执行之前，且要处理「子域已有数据」的冲突。

**由此得到一个关键设计选择：通道合并与 origin 合并可以解耦。**

- 只换资源通道（目录、ZIP 来源、更新流程），**origin 与存档契约保持不变**——这四款继续跑在根域、继续用 `<id>-baseline-v1`；
- 代价是 `AssetAccessPolicy` 与 `ResourcePolicy.compatible` 要对这四款保留特判（「动态条目但用 legacy 契约」）；
- 收益是**存档零迁移、零风险**，改造量从「加 1–2 天」降到「半天」。

反过来，如果连 origin 一起收敛，就省掉了永久特判，但要写迁移代码并做全量存档回归。**我建议先解耦**：先解决「通道」这一件事，origin 统一留作后续独立议题。

### 5.2 首启离线体验

现在装完 APK 就能玩这四款。取消打包后，新装用户首次进来看到的是空大厅，需要联网才能拉目录、下资源。

三种处理：

| 做法 | 说明 | 评价 |
|---|---|---|
| **接受联网** | 大厅本来就要联网拉目录 | 最简单，但首启体验有落差 |
| 保留打包作初始副本 | APK 仍带资源，只是目录走 expanded | 要维护「打包版本 vs 目录版本」的一致性，容易两头不同步 |
| 打包首启引导页 | 空大厅 + 「一键下载推荐四款」 | 体验折中，多一点 UI 工作 |

我倾向第一种，理由是：动态通道本来就是这个模型，二十几款游戏都这样，没必要为四款开例外。但要接受「刚装完、没网 = 没游戏」。

### 5.3 老 APK 怎么办

`versionCode < 8` 的老 APK 只读 v1 目录，且要求严格四款。本方案不动 v1 的**内容**，只把 v1 冻结在当前位置：

- 老 APK 继续拿到这份冻结目录，四款仍然显示、仍然能玩（内置资源在 APK 里，与目录无关）；
- 但它们**永远收不到这四款的新版本**——新资源只发 expanded；
- 还有一个隐性期限：目录签名带 `expiresAt`，有效期上限 90 天。冻结不等于永久有效，**过期后老 APK 刷新目录会失败**（内置资源仍可玩，只是拿不到目录）。

所以「冻结 v1」必须配一条运维动作：每 90 天内重签一次 v1 目录，只改 `issuedAt`/`expiresAt`，内容与 contentCode 不变。否则老装机在某天会突然「看起来一切正常，但目录刷不出来」。

如果不打算长期维护老装机，就要明确接受「老 APK 停在当前版本，直到玩家升级」。

## 6. 建议路线（若将来执行）

**阶段 0 · 前置**
排序字段（`order`）与 `order` 的目录支持先落地。本方案会让四款进入游戏目录弹窗，排序逻辑那时候必须已经能覆盖全部 28+ 款。

**阶段 1 · 通道合并（核心，半天 + 一次发版）**
1. `DynamicGamePolicy.validId` 移除四款排除，同时把 `MAX_GAMES` 容量核一遍（现 100，26+4 无压力）；
2. `resource-releases.lock.json` 四条的 `contentCode` 续值并入 `dynamic-sources.lock.json`（**从 v1 当前值起，不重置为 1**，否则客户端会误判降级）；
3. `AssetAccessPolicy` / `ResourcePolicy.compatible` 对这四个 id 保留 legacy 契约与根域 origin；
4. expanded 目录发布后，新 APK 端验证四款出现在「游戏目录」且已装状态正确；
5. **此阶段 v1 不能动**，老 APK 仍走 v1。

**阶段 2 · 去打包（一次发版）**
1. `bundle.mjs` 允许内置集合为空；
2. `loadBundleManifest` 支持「无内置」分支；
3. `ResourceStorePolicy.BUILTIN` 退化为空集或被删除；
4. 发新版 APK，`versionCode` 递增，`minHostVersionCode` 相应调整。

**阶段 3 · v1 收尾**
1. v1 冻结在当前 seq，转「只重签不更新」；
2. 文档与发布手册标注：v1 已进入维护状态，新功能只在 expanded；
3. 观察老装机比例，决定何时彻底停签。

## 7. 验收清单

- [ ] 老 APK（v0.5.0 / v0.5.3）读 v1：四款仍显示、仍可进入，存档不丢
- [ ] 新 APK 读 expanded：四款出现在游戏目录，首次安装可下载并启动
- [ ] 存档连续性：升级前后 conway 世界 / eml 项目 / light 关卡 / turing 程序均存在
- [ ] 首页不重复渲染（同一 id 不能同时出现在「内置」与「已安装」两段）
- [ ] 目录自检通过：四个 id 不再被 `validId` 拒绝，`storageContract` 与客户端期望一致
- [ ] 降级保护：新 APK 不能把 expanded 里四款的 contentCode 判成低于已装版本
- [ ] 容量：APK 体积下降量 = 四款资源体积之和

| 档 | 范围 | 估算 |

| **A（推荐先做）** | 只换通道：改六处中的 1–4 + 目录并入 + 发一次 APK | 约 1 天 |
