# N20 EML 资源兼容更新设计

- 版本：1.0
- 状态：按固定来源候选实施
- 固定上游：`cb408648ad4233baba757a530aa39278ecdb5127`
- 资源版本：`1.3.1`；内容编号从 `2` 提升到 `3`

## 目标与边界

1. 只更新 EML 静态游戏资源 ZIP 和签名累计资源目录，不生成 APK。
2. 大厅适配器仅在独立上游检出中生成资源，不修改 `D:\soft\EML` 原仓。
3. 保留上游新增的 `function-structure.js` 页面行为；所有打包输入必须绑定完整 SHA 与 Git blob。
4. 使用已审核的 EML 旧版读取器投影基础可读状态，并在兼容封套保留完整新档。
5. 未知/损坏扩展必须阻断，不得回退到静默丢字段的旧存储路径。

## 设计

- 锁定 EML 默认分支提交、构建输入闭包、依赖许可及内联顺序。
- 将适配器的输入摘要和脚本注入清单更新到固定提交；上游新模块 `function-structure.js` 放在应用脚本之前，并检查最终 HTML 引用与执行顺序。
- 在兼容层维持 `schemaVersion: 2` 基础投影；完整新版 JSON 作为受摘要绑定的扩展保存。旧读取器编辑已知字段后产生明确冲突；用户可导出或恢复原始全文。
- 资源来源锁更新 revision，静态资源发行锁只递增 EML contentCode。其余静态 ZIP 内容编号和字节摘要须与已发布当前值完全一致。
- 候选先独立构建两次并通过旧/新读取器夹具，再执行匿名历史预检、生产公钥验证、签名、上传与线上全历史核验。

## 风险控制

- 新上游页面改动较大；适配标记、依赖顺序或输出文件集任一不匹配即阻断。
- 旧版基础投影会忽略组合函数细节；完整定义必须保存在扩展中，不能把投影称为完整兼容。
- 此设计不允许把图灵机、Lambda、路流或元胞实验室顺带带入同一发行。
