# 游戏大厅 v0.3.0：启动提醒与子游戏资源更新设计

- 日期：2026-10-03（Asia/Shanghai）
- 状态：规划草案，未实现；兼容 v0.2.0 的离线内容、数据 origin 和 APK 升级信任。
- 对应：[需求与测试用例](需求与测试用例-v0.3.0.md)、[实施计划](实施计划-v0.3.0.md)。

## 1. 当前事实与设计目标

当前 `MainActivity` 从 APK 的 `bundle-manifest.json` 生成四卡，`WebViewAssetLoader.AssetsPathHandler` 读取 `/assets/games/<id>/`，路径白名单为全量内置清单。`ApkUpdateManager` 只在手动点击时查询 GitHub 最新正式 Release。现有 APK 未实现外置资源、启动检查、资源签名或恢复功能。

新设计目标：本地首屏优先；启动后自动提醒；每游戏独立下载；单会话固定资源版本；存档与 URL 稳定；发布身份独立校验；中断时完整旧版可用；资源通道与 APK 通道互不干扰。

## 2. 模块与数据流

```text
APP 启动 → 本地大厅与资源选择 ─────────────────→ 离线进入游戏
                │
                └→ UpdateCoordinator（异步、生命周期与并发控制）
                      ├→ ApkUpdateManager → 最新正式 APK → 用户确认系统安装
                      └→ ResourceCatalogClient → 签名目录 → 更新提醒
                                                   │
                                         GameResourceManager
                                      下载 → 校验 → 暂存 → 等待生效
                                                   │
                                         GameResourceStore
                                  完整版本目录 + 原子状态文件
                                                   │
                                         GameContentResolver
                         固定 origin/URL → 会话绑定版本的已登记资源
```

`MainActivity` 保留界面与导航协调，把检查策略、网络、验签、解压、持久状态与资源寻址分别放入独立类。网络和磁盘工作不在 UI 线程；应用范围单个协调器持有任务，Activity 订阅状态，不捕获失效 Activity。APP 转后台时取消下载，持久结果保留；旋转不创建第二个任务。

## 3. 启动检查和提示策略

1. 先读本地状态并展示大厅。已有更新提示可立即展示，但带检查时间，不把旧缓存称为刚检查。
2. 每进程冷启动发起一轮 APK 与资源元数据检查；无可用网络只标“未检查：离线”。前台恢复间隔 30 分钟，手动检查可立即触发；已有检查复用任务。
3. 两条通道独立成功/失败。成功且没有更高兼容编号才可显示该通道“已是最新”；网络失败、304 无可用缓存、签名失败不能得出最新结论。
4. 大厅汇总提示条展示可更新、下载中、准备好和本次已更新。详情列出各游戏实际/目标版本、摘要说明、包大小及兼容性；文案按纯文本显示，不渲染远端 HTML。
5. 不自动弹窗或打开安装器。正在游戏中时结果只记入状态，返回大厅才展示。未处理更新持续保留；本次更新成功提示在用户查看详情后可收起，实际版本仍在卡片可查。
6. 自动资源下载仅在大厅前台、未发生下载互斥、设置允许且网络满足条件时启动。APP 退后台、进入游戏、网络不满足设置时停止并清理未完成文件；取消后本轮不自动重试。每轮单游戏最多尝试一次，下次检查才重新排队；同失败编号经恢复隔离的除外。
7. 元数据使用 ETag/缓存、10 秒连接和 15 秒读取超时，每通道总预算 30 秒；资源下载总预算 10 分钟，读取无进展 30 秒取消。403/429 按 `Retry-After` 或 `X-RateLimit-Reset` 退避，无有效头默认 1 小时；手动检查不能绕过服务端退避。ETag 不被视为匿名请求额度无限。

## 4. 发布通道

沿用公开仓库 `xiaoxuhui/game-hub`，不引入新的服务器或客户端凭据。

| 用途 | API/Release 约定 |
|---|---|
| APK | `/repos/xiaoxuhui/game-hub/releases/latest`；正式、非草稿、非预发布、`vMAJOR.MINOR.PATCH`、唯一 `game-hub.apk` |
| 资源 | `/repos/xiaoxuhui/game-hub/releases/tags/game-resources-v1`；固定标签、非草稿、**必须预发布**，不参与最新正式 APK |
| 目录 | 资源 Release 的唯一 `catalog.signed.json` 资产；单文件同时承载负载与签名 |
| 游戏包 | 同一资源 Release 中的 `game-<id>-<contentCode>-<sha256前12位>.zip`，上传后不替换同名内容 |

资源 Release 使用预发布标记是通道隔离约定，不表示其目录内容未经验证。客户端仅在此固定标签通道接受资源，不扫描任意预发布。原 v0.2.0 客户端继续只读 latest 正式 APK；发布操作必须检查该标记和 U39，错误地改为正式 Release 属发布阻塞。

先上传并确认所有 ZIP 的 asset ID/大小/摘要，再离线签署新目录，最后替换单一 `catalog.signed.json`。GitHub 替换资产期间可能暂时 404；客户端保留上次签名目录并标注检查失败，不混用新旧目录。目录下载及 ZIP 使用服务端 asset ID 在固定 API 路径构造地址；重定向沿用现有 HTTPS GitHub 下载域名白名单，不接受目录里的任意 URL。每个候选所需资产固定在一份验证后的目录快照中，目录变更不会改变在途任务目标。

## 5. 签名目录协议 v1

外层文件为 UTF-8 JSON，字段：`envelopeVersion=1`、`keyId`、`payloadBase64`、`signatureBase64`。严格限定字段类型与长度；未知协议/keyId拒绝。签名采用 RSA 3072、`SHA256withRSA`，验签对象为 Base64 解码后的**原始 payload 字节**，不把解析后 JSON 再序列化验签。公钥随 APK 固定；算法由协议固定，不能由下载文件指定弱算法。

通过验签后才解析 payload，拒绝重复 JSON 键、非法 UTF-8、非整数与溢出。基础结构如下（字段定义，不是已发布目录）：

| 字段 | 定义 |
|---|---|
| `schemaVersion` | 固定 1 |
| `channel` | 固定 `game-hub-resources-v1` |
| `catalogSequence` | 正十进制字符串，范围 1..2^63−1，严格递增 |
| `issuedAt` / `expiresAt` | UTC 时间；最长有效期 90 天，用于检查缓存陈旧，不替代递增编号 |
| `games` | 四个固定 ID 每个恰好一项；新游戏需升级大厅支持 |
| `game.id` / `version` | 固定 ID / 展示版本，限制文本长度 |
| `contentCode` | 1..2^31−1 的整数；同游戏严格递增；内置版本也有编号 |
| `sourceRepository` / `sourceRevision` | 固定仓库白名单 / 完整 40 位 Git SHA |
| `minHostVersionCode` / `maxHostVersionCode` | 闭区间大厅兼容范围，不使用模糊版本字符串判断 |
| `resourceProtocol` / `storageContract` | 本版资源协议 1 / 已登记的双向存档兼容标识 |
| `entryPage` | 该游戏允许的相对入口，不允许修改为外部地址 |
| `assetId` / `archiveBytes` / `archiveSha256` | 同通道发布资产的整数 ID / ZIP 大小 / 完整 SHA-256 |
| `files` | 相对路径、实际字节数、SHA-256、固定 MIME 类型的完整清单 |
| `releaseNotes` | 限长纯文本说明 |

最高有效 `catalogSequence` 和对应 payload 摘要持久保存：小于最高值拒绝；同序号只有相同摘要可接受。每游戏已接受最高 `contentCode` 与摘要也保存，同编号变内容拒绝。已接受目录过期时不自动下载新包；已经激活资源仍离线可玩。首次安装没有服务器时间可信依据，设备时间异常时停止自动资源下载，展示原因，已知版本不受影响；不能声称本方案完全防止全新安装客户端遇到历史有效目录重放。

发行撤回有缺陷资源时，目录发布**新的序号和资源编号**，可用旧源 SHA 重新构建兼容资源，不降低编号。用户本地恢复是显式选择可信旧副本，不清除最高编号记录；本地隔离的编号不会被自动再次应用。

资源签名私钥与现有 APK 密钥独立，仅在仓库外签名，CI 生成未签名候选。私钥不进入源码、APK、Actions secrets、工件或日志；公开公钥和验签结果可归档。v0.3.0 首次公开前资源签名密钥完成异机备份恢复演练。公钥更换通过同证书 APK 升级，v1 不实现目录自授予新公钥。

## 6. ZIP 安装与存储

```text
filesDir/game-resources/
  state.json                 原子提交：active/previous/ready、最高编号、隔离记录
  catalog-cache/             最后验签通过的目录与 ETag
  versions/<id>/<code>-<完整摘要>/   完整版本目录，安装完成后只读使用
  staging/<随机任务ID>/       未激活的下载与解压，重启可清理
APK assets/games/<id>/        永久离线基准
```

预设上限：目录外层 1 MiB，payload 512 KiB；单 ZIP 25 MiB，实际解压累计 100 MiB、单文件 20 MiB、最多 2000 文件、相对路径最长 240 字符、最多 16 层。所有上限按流式**实际读到的字节数**计，不信 Content-Length 或 ZIP 声明。压缩比最多 100:1；未来超限资源需重新评审。持久资源预算 300 MiB，预留 20 MiB 空间余量；空间不足时先清理不活动、不被会话引用的过期版本，否则拒绝新包。

安装顺序：校验目录身份与兼容 → 检查预算 → 下载 `.part` → 核对实际大小/ZIP SHA → 新 staging 解压 → 每文件白名单/大小/SHA/类型核验 → 确认入口和必需资源齐全 → 将完整目录移动到同文件系统的 versions → 用 `AtomicFile` 写状态 ready → 在安全进入边界原子切换 active/previous。所有状态写入由同一锁串行化；AtomicFile 不代替并发锁。

仅接受规范相对路径，拒绝 `..`、绝对路径、反斜杠、盘符、空/NUL、非规范分隔、重复条目、同路径大小写冲突、文件/目录前缀冲突；canonical 路径必须在 staging 内。ZIP 只允许普通文件和目录，不创建符号/硬链接，不执行归档脚本。资源文件需与签名清单完全一致，清单外文件与缺失文件都拒绝。整个候选失败即不激活，旧 active 不受影响。

重启时以 state 中引用的完整版本为准，核验目录身份和文件完整性，拒绝失效指针；未引用的半成品清理。完成目录移动但状态未提交仅留下可清理孤儿，不猜测激活。状态损坏时仅选择可验证且存档兼容的已知副本；无法安全确认则给出恢复说明，不静默删存档。垃圾回收绝不删除 active、previous、ready 或仍由会话引用的目录，至少保留内置与一个兼容 previous。

## 7. 资源加载和会话一致性

保持 `https://appassets.androidplatform.net/assets/games/<id>/<entry>` 不变；由 `GameContentResolver` 在同一路径选择内置 assets 或校验后的私有版本文件。自定义 PathHandler 必须只暴露游戏版本目录中的登记文件，不能直接映射整个 filesDir。

每次进入游戏建立不可变 `GameSession`：游戏 ID、资源编号、根目录、逐文件白名单、数据兼容标识。在打开页面前激活 ready、清理网页资源缓存（不清理存档），WebView 使用禁止旧资源缓存的策略，响应采用 `Cache-Control: no-store`。该会话内的主文档、关卡页、iframe 和 Worker 使用同一 resolver；不能在 `shouldInterceptRequest` 中每次读取可能变化的 active 指针。离开后销毁 WebView 并释放版本引用。

继续限制同游戏主页面导航、登记资源请求和外部链接；跨游戏资源读取沿用共享 origin 的已知边界。更新激活只能在**没有任何游戏会话**的大厅边界发生，确保当前会话不会读到另一个游戏新旧混合资源。禁止资源新增 Service Worker 注册；构建检查、WebView 拦截及升级验证覆盖旧缓存，不仅检查入口 HTML。当前真实源码是否已有 Service Worker、缓存或其他写入策略在实施 M1 前逐项核实，未核实不标通过。

## 8. 存档和恢复边界

现有 origin 与 `conway-life-game.*`、`eml_workbench_v2`、`light-game/save`、`turing-machine-simulator.*` 等已知键保持稳定。路径不同不构成存储隔离。更新前后既测试目标游戏，也测试其他三游戏数据不受影响。

每游戏登记 `storageContract`，内置基准与可自动更新资源必须满足同一双向读写合同；发布验证覆盖“旧存档→新资源写入→旧资源再读写”。本版不通过下载目录声明来推定兼容，合同是维护者验证后签署的发行声明。不能确认兼容的资源停止发布到此通道，留给后续有完整迁移设计的大厅版本。

加载故障指可检测的主入口/必需文件失败，不把页面加载成功当作玩法正确。发生故障关闭会话，隔离失败编号，展示恢复按钮；恢复需确认 previous 或内置仍在当前存档合同内。手动恢复不清数据，不承诺恢复之前的进度快照。语义/玩法错误可能只能靠用户恢复和维护者发布修复，不自动后台切回以免打断用户。

## 9. APK 与资源版本的交互

v0.3.0 计划 `versionName=0.3.0`，`versionCode` 至少 3，发布前与实际正式历史复核，不在本轮改代码。APK 和资源编号独立，资源更新不改变 APK versionCode。

新 APK 的 bundle manifest 为每游戏增加内置 `contentCode`、`resourceProtocol` 和 `storageContract`。启动选择最高编号且与当前大厅/存档合同兼容的已知完整资源；用户显式恢复选择优先且不能被普通自动检查撤销。内置已追平下载资源时可回收重复副本；版本较低的 APK 内置资源不能自动覆盖更高兼容下载资源。新版 APK 必须能识别旧状态；不兼容的已下载资源需明确停用并走兼容恢复，不能忽略存档合同直接启动内置版。

同时发现大厅新版与子游戏新版时，可先处理兼容当前大厅的资源；要求更高大厅版本的显示“先更新大厅”，不得先安装。APK 升级保留应用数据目录，升级后重新计算兼容范围和检查提示。

## 10. 生产、审计与验证

资源生产只读消费固定 SHA；独立检出构建、完整清单、资源协议/存储/原生桥/许可扫描、四游戏回归通过后形成候选。资源 ZIP 的时间戳、顺序和编码固定，保证相同输入可复核；编号映射登记在大厅仓库，原始四仓库基线记录不移动。

实施时按 U22–U44 建立纯策略单测、文件安装故障注入、签名/篡改夹具、Android 仪器与模拟器测试，以及真实设备验收。U38 验证 0.2.0→0.3.0 同发行证书覆盖并保留四游戏实际数据，随后用递增 APK 夹具验证启动提醒与安装；夹具不是正式发布。U39 需在资源通道实际建立后匿名复核旧客户端 latest 查询，规划阶段不声称已验证。

## 11. 官方依据

- [WebViewAssetLoader 私有目录处理器](https://developer.android.com/reference/androidx/webkit/WebViewAssetLoader.InternalStoragePathHandler)：支持私有文件加载；本设计额外加入版本选择与资源白名单。
- [AtomicFile](https://developer.android.com/reference/android/util/AtomicFile)：用于完整状态文件提交；应用另行负责同步和目录事务。
- [Android ZIP 路径逃逸防护](https://developer.android.com/privacy-and-security/risks/zip-path-traversal)：解压路径需应用验证，不假设所有支持设备自动防护。
- [GitHub Release API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)：latest 正式 Release 与固定 tag 查询分开。

以上是技术依据，具体上限、协议、生命周期和 UI 策略是本项目的设计选择，尚未通过实现验证。
