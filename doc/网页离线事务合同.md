# 网页离线事务合同

状态：VERIFIED（W2.1a内部账本/真实IDB）；独立OPEN/P2已按红绿证据批改并终审CLOSED。账本只是内部协调组件，不是验签器、缓存完整证明或可运行授权。

## 1. 数据库边界

独立数据库`game-hub-web.resources.<basePath>`、版本1、单state store/key，不访问或迁移游戏saves数据库、localStorage。完整根形状固定schemaVersion/revision/nextFence/installations/sessions。不存在记录是首次；未知/损坏记录拒绝所有写操作并保留原数据。请求阻塞/版本变化/配额失败明确失败，无自动deleteDatabase或重建。

读改写在一个readwrite事务的get.onsuccess同步执行；不把验签、fetch、Cache或任何await放入事务。返回值只在transaction.oncomplete后成功。纯reducer复用同一字段/状态/预算校验，单个state记录让不同游戏/窗口的空间预留串行化。

## 2. 身份与预算

安装记录字段：id（游戏ID）、contentCode、digest、fence、cacheName、bytes、phase、proofHash。proofHash是上层验证完整签名原字节摘要；账本不接受该摘要本身作为签名已验证的证据。cacheName只能由账本根据basePath哈希与单调fence生成，不能外部指定。版本身份三元组唯一；fence全局单调增加，安全整数耗尽拒绝。

bytes为上层计算的完整文件及证明/完成标记保守预算，正安全整数；全部记录包含staging/ready/active/retained/failed/repair/deleting，均计入150MiB总额，始终留20MiB安全余量。取消/错误/崩溃不直接释放，只有完成可证明的专属缓存删除、同fence提交移除才释放。故障注入证明不能借并发或旧回调超预留。已存在同版本任务拒绝新建，不重复增加预算或复用fence。

## 3. 转移与会话

- begin创建staging、分配fence/缓存名并预留预算。
- complete仅同fence的staging及matching proofHash/完整清单摘要可变ready；上层须在此之前完成全部文件/完成标记验证，并在提交前重新验证新鲜目录。
- cancel仅staging→failed；迟到complete/cancel不得触及另一任务或变更失败记录。
- enter只允许ready/active，生成唯一会话引用并将该版本active；原active变retained，已打开会话保持旧完整身份。引用包括sessionId/clientId/controllerProtocol/id/contentCode/digest/fence，重名/错身份拒绝。这条内部转移不是对未受控页面授信，入口与SW需另外完成身份/完整校验。
- leave只移除精确sessionId/fence引用；未知或冻结客户端引用不按心跳/超时删除。恢复和BFCache使用原引用；首版无自动回收。
- missing只允许ready/active/retained→repair；不更改存档或删除引用。
- begin-delete仅failed/retained/repair，且账本无会话引用；上层还须给出同fence、完整客户端枚举/协议/阻断新入场的屏障凭证。active/ready/staging拒绝删除。未知枚举、可能冻结客户端、活动缓存或迟到写入未收束时禁止提供凭证。
- deleted仅同fence的deleting且明确cacheAbsent=true；移除记录后才释放预算。删除中崩溃保持deleting并拒绝运行；不能把部分缓存当完整旧代恢复。

所有事件未知字段/类型拒绝；错误不改变原state。持久证明的真实签名/固定公钥入口、Cache写入和每次运行完整性由后续W2.1b/W2.2实现并独立验收；本片不注册SW、不开放已保存状态。

## 4. W2.1c收据与状态的比较后提交（实现前合同）

仍使用同一版本1数据库/state store；除current账本外，增加authority键（当前已接受的完整签名收据）及proof:<payloadSha256>键（被安装记录引用的不可覆盖证明）。不改变游戏saves或首版账本root形状。get/getKey区分真正不存在、已有undefined与未知格式；无authority但有安装记录是修复/暂停情形，不从孤儿proof或Cache推断可信水位。

snapshot在短只读事务读取账本、authority及去重后的所有被引用证明；证明读取累计上限150MiB。异步阶段使用当前固定信任工厂逐一restore，并以原文验证authority对每个安装proof的连续性（sequence/shell/全部游戏计数与身份/命名空间/时钟水位不得倒退），不能仅独立验两个有效签名就接受单键回放。重新绑定payload SHA、游戏id/code/digest与保守预算；缺失/未知/校验失败拒绝新操作，保持原数据。bytes必须等于该游戏完整文件总和+证明envelope字节+证明元数据UTF8字节+1024完成标记预留；proof共享可以保守重复计费，不能少计。authority额外副本限制8MiB，包含在20MiB保留余量中。

snapshot token覆盖完整ledger JSON以及authority原封装SHA/全部元数据/字段集合；原子readwrite事务重新读取并比较全部被引用proof的原文token（即使complete/cancel没有新proof写入），而非只比较revision或信任可自报的receiptSha256。任一token变化拒绝，本次无写入。所有异步Crypto/fetch均在事务前；调用输入同步复制，事务内只有IDB请求回调和同步运算。成功在oncomplete后返回。

带新authority的事务在同步提交决策及最后一次写请求成功回调再次按真实clock检查notBefore/expiresAt；排队期间到期即abort整个事务。这里的期限检查是在最后可中止的JS回调，不声称能把物理磁盘落盘时刻与时钟做硬件原子操作。内部数据库测试可注入clock，正式固定入口不允许覆盖。

- check：按实际now新鲜验签，使用snapshot恢复的当前已签历史；CAS后同时写新authority和递增ledger revision。失败不保存“已成功检查”。
- begin：同样先新鲜验签且游戏available，原子保存authority、分配账本fence/预留预算、首次proof。若同payload proof已由snapshot真实验证，比较原文token后保留原证明；未被账本引用的孤儿proof冲突则停止，不盲覆盖。
- complete：读取同fence staging、重新新鲜验证当前authority；只有payload SHA仍与任务proofHash相同、未过期且上层提供完整清单验证结果，才CAS提交ready/authority。同期间目录任何新代变化时保守停止，用户重试；cancel只变failed，迟到complete失败。
- cancel及后续会话状态写操作也比较snapshot，不能以通知代替锁；此次未接Cache，complete仍是内部调用，只有随后受审安装器可在完整文件检查后调用。

proof从不覆盖。未来删除释放预算前必须同时证明并清理专属Cache和不再引用的proof；当前无自动回收。正式openPinnedRepository只允许indexedDB/origin/basePath，内部使用固定公钥及真实Date.now，不向产品用户暴露trust/clock替换接口。纯内部工厂的可注入测试身份/时钟不是正式安装入口。
