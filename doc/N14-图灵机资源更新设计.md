# N14 游戏存档入口盘点与图灵机手动恢复设计

- 版本：N14
- 状态：实施中
- 实施策略：先逐项盘点所有在册游戏，再针对可保存用户数据但缺少导入/导出的项目补齐；图灵机沿用现有资源适配、内容编号和签名历史。

## 设计目标

1. 让图灵机每次启动都进入默认新会话，由用户主动导入文件恢复需要的状态。
2. 读取存档只用于检查与保护，不自动载入、不覆盖；真实编辑触发自动保存前先保护原完整档。
3. 保持旧版 reader 可读取基础项目；Max 兼容值只能来自可验证、明确记录的既有限制。
4. 盘点大厅全部在册游戏的用户数据能力，给有用户数据但缺少导入/导出的项目补齐安全的 JSON 入口。
5. 以来源 SHA、schema、导入失败边界、桌面/手机交互和资源摘要验证交付。

## 存档边界

新版完整项目保留上游的 `maxSteps: null`、未知字段及原始文本。为旧版生成的兼容视图不得从 Max 包装、缓存、普通历史、时间戳或可编辑元数据推断有限配置；旧 C4 还允许任意输入兼容上限，因此现有 `legacyMaxSteps`、旧 reader 读回成功和字段匹配均不能证明该值属于真实有限项目。

唯一允许的有限配置来源是用户主动选择的一份独立有限项目原档：`maxSteps` 为有限正整数，不含 Max 扩展/包装；用户明确要求关联后，适配器解析该文件，并与当前 Max 项目比较，除 `maxSteps` 外全部旧 reader 已知字段必须相同。原档字节和摘要随迁移历史保留。任一字段不匹配、文件来源无法被识别为基础有限格式或用户未明确关联时都拒绝建立关联。该来源是用户提供的真实有限项目设置，不声称能从不可验证的历史元数据证明其创建时间。

没有此类显式有限原档时，不写兼容视图。若用户只有 Max 文件和旧 C4 生成的包装，继续支持 Max 文件运行和完整导出；不生成、不改写旧版镜像。不能事后把 Max-only 项目缓存、旧包装或快照转成“切换前来源”。

若 Max 完整档没有上述显式关联的有限原档，新版仍可运行和完整导出，但不得新建或改写旧版镜像；如现有旧镜像存在则保持原字节，直到用户导入并明确关联匹配的有限原档。普通时间戳、旧包装、缓存、快照和历史均不提升为可信来源。

完整文件将兼容视图和完整原文绑定；旧 reader 只读取有限视图，忽略扩展字段。图灵机存档是一份项目对象而非带多个记录 ID 的集合：冲突合并以该项目存储键作为稳定身份，仅将旧 reader 可读的已知字段合并到同一完整项目，保留完整档的未知字段。用户选择应用旧版编辑后，明确以实际有限 `maxSteps` 结束 Max 模式；选择恢复完整档时，旧版修改原文作为历史保留；取消时两份源数据不变。

已发布图灵机 0.6.0/content3 的来源 `ec1b` 已包含 `ffca` Max 功能；本轮不再从旧版 `ffca` 单独构建或重复发布。现有启动逻辑会把保护记录自动恢复到页面，本轮将改为仅检查并保全记录，渲染默认项目。旧记录保留；第一次真实编辑时先把旧完整原文写入历史，再保存当前新会话。遇到损坏/冲突/容量不足时进入只读会话并允许完整导出。导入继续由原来的文件选择器触发；显式导入成功后才载入文件状态。

## 构建和发布边界

- 原始仓库只读。使用归档 bundle 在独立检出目录构建。
- 每个资源只读取锁定 SHA；来源证明列出完整输入和输出 SHA。
- 仅对确有代码变化的资源提升 contentCode；其余游戏 ZIP 字节及内容编号保持不变。
- 上传图灵机 ZIP 后再发布新签名目录；保留旧签名目录和 ZIP 历史。
- 不构建、不签署、不上传 Android APK。
