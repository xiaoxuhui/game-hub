# N6 兼容资源局部更新计划独立审阅

- 受审提交：`0f15afa679a50cbfd019186d4401d5429d47e394`。
- 范围：`doc/N6-资源局部更新实施计划.md`、v0.4 总计划索引及 N5 独立意见归档；对照现有动态资源生产/签名校验边界。仅只读审阅，未改 main、原六游戏仓库或发行状态。检查时主仓库工作树干净。

## 结论

**无阻塞，可进入示范功能切片。** 计划先提交并独立审阅 `examples/memory-demo` 的兼容功能，再以该已存在的完整源码 SHA 更新来源锁，避免来源锁/当前提交自引用；`dynamic-resources.mjs` 当前候选确实绑定 `bundleCommit` 与来源锁 SHA、并比对独立来源检出的每个提交 blob。`core.js`、存档 schema/key、origin 和原生桥均冻结，升级仅涉及焦点连续与提示，仍需真实浏览器和正式 Android 客户端的旧存档回归。

固定 `game-resources-v2` Release ID/tag 不移动，先上传新 ZIP、保留旧 ZIP，旧签名目录按序号/摘要归档，再发布新 `catalog.signed.json`；显式核旧目录 SHA/序列、生产 APK 公钥和完整分页资产归属。这个顺序与客户端签名目录/资产 ID 绑定机制相容。目录切换期间若旧 catalog 被删除而新目录未上传，客户端短时失败并保留已安装版本；计划没有将这段空窗当成功更新，也没有用临时测试密钥冒充正式签名。

验收要求正式 v0.4 在 APK SHA `c6e071e18eac1cb97f3d898d6eb4dab2c790b8d9310a907a7e44e3c34a78ee39`、code4 不变的情况下发现、下载并激活 #2/version1.0.1，旧进度保留；N7 两新游戏与 N8 集中清理仍是独立待办。没有把 N5 发行结果误称 N6/N7 已完成。

## 实施时应保留的核验细节（非阻塞）

1. 在上传前后分别归档正式 AVD 的 `memory-demo` active 身份、内容编号及 **同一条实际存档的规范化状态或摘要**；完成局部更新后先确认运行中会话仍为 #1，退出重进才是 #2，并在进程重启后核旧存档原值。单凭“有 1 步”可能由新版重新操作得到，需以同一状态身份支撑保留结论。
2. N5 首发在线验收工具曾要求 v2 恰有 catalog + 一个 ZIP。N6 增加旧 ZIP、历史目录资产和新 ZIP 后，该工具会按设计拒绝；后续工具应更新为累计资产清单及完整分页精确比较，保留对未知/重复资产拒绝，避免因旧工具失败而跳过公开资产绑定审计。
3. 历史目录上传名与新 ZIP 名应唯一，旧 `catalog.signed.json` 的原始字节 SHA、资产 ID/归档名和新目录序号/签名可组成发布前后审计链。未知上传结果先只读盘点并与期望快照比对，再决定恢复或继续，计划对此已有方向。

**审阅范围仅为规划。** 真实功能代码、浏览器体验、生产签名与公开资源更新尚未执行，后续每切片提交后仍需独立审阅。
