# 100 款兼容通道规划审阅

日期：2026-11-01；审阅对象 `f31817c3e37e9e0df9c0a7889eb01535a3e1b1c3`。采用与实施者不同的安全和兼容视角自审。

1. **阻塞：双通道不是复制两个资产即可。** 旧目录与扩容目录使用同一个签名格式及客户端高水位；同序号不同载荷、旧目录先于扩容目录更新、并发发行和中断都可能导致升级设备拒绝新目录或错过更新。实施前必须落地严格的顺序、全局序号、跨通道一致性和中断恢复，并用实际客户端验证。
2. **阻塞：旧用户的已安装资源与存档。** 新客户端切换后必须接受原目录的安装证明，保留状态和哈希；旧 APK 回退时已有大于 16 项的大厅状态也需要明确处理，不能仅证明 JSON 格式可读。
3. **阻塞：扩容后的包大小和 API 预算。** 100 个条目可能突破现有 512 KiB 载荷和 4 MiB 资产列表；应测量真实和极端边界，不能只调数量常量。
4. **阻塞：现有旧通道签名工具无法保证扩容目录同步。** 启用后不得允许旧工具单独更改当前目录而造成过期、遗漏更新或错误顺序；需要可重复、可恢复的同步发布工具和测试。
5. 初始扩容目录复制旧签名目录可使等序号等摘要迁移，但以后须保留旧客户端所需目录续期；资源通道必须先验证，APK 后发布。用户指定分组暂缓，不纳入。

结论：设计方向可继续细化，以上四项未解决前不可将方案标为通过或发行生产 APK。待实现后逐项验收并归档结果。
