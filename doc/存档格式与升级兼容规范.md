# 存档格式与升级兼容规范

- 版本：1.1，2026-10-12（按用户新增双向兼容要求修订）
- 状态：设计规范；现有游戏逐项接入待办，尚不是已实现的存储协议。
- 适用：大厅资源更新、独立网页/独立 APK 升级和回退。

## 1. 三个独立版本

游戏功能版本、大厅资源 contentCode、存档基础格式各自管理。基础格式和已有字段含义保持稳定；新增功能优先放在可忽略的扩展字段中，旧 reader 可读取已有内容，只忽略不认识的新字段。不能把已有字段改成旧 reader 不接受的类型，或让新增字段成为旧 reader 读取基础数据的必需条件。APK versionCode、资源 contentCode、目录 sequence 只增不减。

保留已发行 reader 可接受的原外层结构、schema 标识和基础字段；不能直接用新 envelope 包住旧数据，或单纯提高 schemaVersion 后声称旧 reader 能读。未来新增兼容声明可放入其已验证允许的 extensions/元数据，版本化扩展记录 writerVersion 和 feature。每游戏发布合同声明兼容基础格式、固定旧 reader SHA、扩展规则、所需大厅能力、迁移及读写往返测试摘要。无法提供旧格式兼容视图的破坏性格式变化，自动发行必须阻塞。

已经发行的旧 reader 行为不能凭文档改变；例如已知 Lambda 旧 reader 拒绝 v3、图灵旧 reader 拒绝 null。新版必须生成它们能接受的基础格式/兼容视图，并用真实旧 reader 实测。不宣称任意历史版本会自动读任意未来数据。未来稳定兼容基线版本必须主动支持忽略未知扩展；可选历史版本的支持范围逐一列出。

本规范不直接给当前 v1/v2 签名目录加字段；目录严格 reader 的协议演进另做通道/大厅设计，并保持旧通道。

## 2. 升级合同

- 升级能力：新版读取已支持的历史数据并保留含义；必要时通过显式纯迁移函数转换，不偷偷降级数学语义。
- 双向读取是发行要求：新版读旧格式，声明支持的旧版读新版的基础内容，旧版不支持的新字段/功能可忽略。读不到基础内容的候选不能自动发行，不能用恢复检查点代替双向读取验收。
- 旧版读写以后完整原档及未知扩展仍须保留；兼容视图和完整规范存档分开保存，适配层按稳定记录ID合并已知字段。不能将旧 writer 丢弃未知字段后的输出覆盖完整新版原档；已有旧独立APK若做不到，使用保留原文件的兼容导出路径并明确支持范围，未验证往返保护不能称安全回退。
- 升级前检查点作为崩溃/损坏恢复备份；恢复它是单独的故障恢复动作，不能掩盖升级后最新进度丢失。
- 所有版本均保留旧导入格式 reader，直到明确弃用周期、导出工具及迁移路径已有验证；建议至少覆盖全部已发行格式，规模增大后再制定保留周期。
- 自动兼容视图可不展示旧版未知的新功能，但完整原档保留，不改变已有字段/领域含义。不能靠删除唯一的扩展数据、限制新版功能或改变数学规则来伪造兼容。

## 3. 迁移事务与备份

先校验原档并保存原始字节、摘要、来源资源版本和 schema；在新命名空间复制并迁移，验证领域不变量和导入导出往返；最后提交一个原子指针，使新资源与新 schema 同时生效。失败、中止、存储额度不足则不切换指针，旧资源与原档仍可用。迁移可重复执行，不产生重复记录。备份只留用户设备，默认不上传云端。

这需要具备事务/检查点能力的存储适配层：浏览器 IndexedDB 或等价双槽指针设计；仅多次 localStorage.setItem 不能当作跨键事务。游戏运行会话固定资源版本，退出游戏后才激活。浏览器缓存切换与 Android 资源激活也要遵守同一数据合同。

现有四游戏共享 origin，动态游戏各自 origin；现有大厅恢复旧资源按钮并不自带存档快照。不能在当前实现上声称已有无损数据回退。先在独立适配层实现能力，并为Android资源指针与网页数据指针跨存储提交制定恢复状态机：准备/迁移验证/待激活/提交完成各状态持久化，启动时只选已完成且资源和schema匹配的组合，不能假定两套存储可同时原子提交；需要新的原生检查点接口时另发大厅版本。能在现有网页能力内实现的迁移可随资源包更新，通常不必下载整个 APK。

## 4. 发布门禁

必须在干净固定 SHA 候选运行以下矩阵，产物、夹具、报告绑定 SHA/摘要：

| 测试 | 要求 |
| --- | --- |
| 每个历史 schema → 新 reader | 含义保留，未知字段按格式规则保留，不清空 |
| 新功能保存 → 新 reader | 新功能恢复完整，导入导出往返一致 |
| 新保存 → 固定旧 reader | 已有内容可读，新字段可忽略；旧版读写后完整扩展仍保留，不能仅恢复旧检查点冒充通过 |
| 迁移重复/中断/损坏/未来版本 | 不污染原档、不重复、可恢复，失败消息可操作 |
| 空间不足/断网/重启/并发会话 | 资源与数据指针一致，旧会话不写进新格式空间 |
| 实际设备/浏览器升级与回退 | 真实操作保存、退出、激活、重启及检查点恢复 |

机器门禁和维护者独立审阅归档后允许生产发行；仅类型检查、简单字段扫描或口头兼容声明不能放行。

## 5. 三游戏迁移路线

- EML：保持旧工作台基础结构；组合定义放扩展，旧 reader 所需公式/引用提供经领域验证的兼容表达，不能让未知 EML_COMPOSITION 破坏旧版基础读取。无法提供正确兼容表达则阻塞发行；新版完整恢复组合定义及结果树，旧版只能忽略其不支持的功能。
- Lambda：供旧 reader 使用的基础快照维持 v2，手动归约 paths 放经实测可忽略的扩展或独立完整存档；不能把现有 v3 原字节直接发给只接受 v2 的旧 reader。基础表达式/进度可恢复，扩展会话不因旧版保存而丢失。
- 图灵：基础 maxSteps 继续为旧版可接受的整数；新 unlimited 为扩展模式，完整存档保留无限含义，旧版按已有有限模式读取基础数据（不能宣称旧版支持无限运行）。不可把原字段改成 null 后冒充兼容；有限模式的兼容值需沿用明确记录的旧配置，禁止擅自用1000000伪造数学语义。

## 6. 工程规范接入

各子游戏在自身仓库维护基础格式/扩展文档、历史合成夹具、双向读取及读写保护测试、发布兼容合同。大厅打包器只读固定来源与合同；签名端校验门禁报告并拒绝未满足双向读取的候选。共用开发 skill 引用这份规则或后续唯一真源，避免各项目复制后漂移。将规范接入 mini-app-harness 及实现三个游戏迁移另列阶段，先保留用户本地未提交 skill 改动。

## 7. 后续历史版本选择

按用户要求加入待办：每个游戏可列出可信历史资源版本并主动选择回退。当前不宣称已有任意历史版本选择；既有恢复/固定机制的能力须按实际UI与测试另行盘点。后续需签名历史版本索引、包摘要/可用性/大厅能力检查、双向存档兼容提示、未知扩展保护、运行中会话固定与安全激活、断网/失败恢复验收。旧版本选择不降低目录反重放水位、不回退contentCode分配器，不移动历史标签或覆盖历史ZIP。
