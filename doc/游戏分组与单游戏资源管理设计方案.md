# 游戏大厅分组与单游戏资源管理设计方案

- 日期：2026-11-01；状态：讨论稿，待产品确认；仅设计，暂不实施。
- 关联：[两款游戏接入设计](两款游戏接入设计.md)、[实施计划](两款游戏接入实施计划.md)。本方案不改变正在规划的两款游戏接入范围。

## 1. 目标和当前情况

大厅采用两级目录：第一级为分组，第二级为组内游戏；提供“全部游戏”和搜索入口，游戏仍按原来的游戏 ID 启动。大厅提供官方默认分组和用户自定义分组；一个游戏可同时属于多个分组。用户可单独下载、更新游戏资源，安装一份后所有分组共用。

当前大厅已有内置游戏和动态游戏、按游戏下载的资源流程；动态签名目录的客户端与构建工具都限制 16 项，客户端还以游戏 ID 管理版本和校验信息。现有代码不支持本方案所述分组管理；分组不能突破目录数量限制。

## 2. 使用方式（建议）

1. 首页展示“全部游戏”、官方分组和“我的分组”，分组卡片显示名称和游戏数量；进入分组后显示游戏卡片，返回回到分组列表。游戏内返回行为沿用大厅现有约定。
2. “全部游戏”包括本地内置、已安装和可在线获取的游戏；离线时展示本地可确认的信息，并标明目录可能过期。可搜索游戏名称，不受分组限制；空组展示空态和添加入口。
3. 未安装游戏卡片显示“下载”，显示大小与网络状态并沿用现有下载确认；下载、校验、安装失败要显示原因与重试，保留已有可用版本。已安装卡片可打开；有新版本时显示更新标记并按单游戏更新。
4. 用户可创建、重命名、排序、删除自定义组；组内可添加、移除和排序游戏。添加时允许多选，并允许游戏同时存在多个组；同一个组内同一 ID 只出现一次。组名允许相同但需可区分，名称、数量、长度等具体上限在实施前定案。
5. 默认分组由发行方维护；用户可隐藏默认组，或复制为自定义组后编辑。默认更新不覆盖用户组、排序或隐藏选择。“全部游戏”是系统视图，不可删除。
6. 删除分组或移除组内游戏仅移除关系，保留游戏资源与存档。卸载资源是单独操作，须明确提示其对所有组生效；内置游戏不提供卸载内置资源。卸载默认保留存档，清除存档须另行明确确认。游戏下架时保留已有资源及用户组关系，显示状态，不自动删除。

## 3. 数据与资源

- 游戏身份：沿用现有稳定 game ID；内置与动态 ID 的命名空间保持现有约束。游戏资源、校验、版本、存档和更新以游戏 ID 为单位，与组分离，不因多组重复下载、复制文件或生成多份存档。
- 官方分组：建议由经签名的发行元数据携带稳定分组 ID、展示名称、顺序、游戏 ID 列表和版本。客户端先验证签名、来源、时效与大小，再应用；引用未知游戏时跳过该项并记录可诊断状态，不影响已验证游戏。游戏归属可多对多。
- 用户数据：在大厅本地独立保存有版本号的数据，包含用户组 ID、名称、成员 ID、顺序、默认组隐藏状态；不存储游戏资源及其存档。用原子写入和上次有效副本防止异常中断丢失；解析失败时保留原文件并报告恢复入口，不静默重置。
- 合并规则：官方数据只决定官方组；用户组、成员和排序以本地数据为准。官方更新不会删除或改写用户关系。引用已下架或暂未获取元数据的 ID 时保留关系并显示占位状态。组内按 ID 去重；系统视图动态生成，不存成用户组。
- 备份：建议提供显式导出/导入分组配置，默认不包含游戏存档和资源；导入前校验大小、版本、重复 ID 和字段，展示预览并由用户选择合并或替换，替换前保留备份。旧版本读取新格式时忽略不认识的可选字段；若主版本不兼容则拒绝写回并保留原文件，避免丢失新字段。是否跨设备同步留待另行设计，默认不上传个人分组。
- 分组修改不得更改资源签名、信任密钥、版本选择、隔离状态或游戏存档。官方分组更新与资源目录更新失败互不破坏上次可用结果。

## 4. 数量与兼容

建议新的大厅客户端支持最多 100 个动态游戏（另有四个现有内置游戏），分组引用次数不计入游戏数量；组数、每组成员数、目录大小和本地存储上限须在实现前结合现有文件大小和内存预算制定并测试。100 是可配置安全上限，不宣称无限。目录和包的签名、哈希、大小及路径检查继续生效。

已发布客户端硬编码动态目录最多 16 项；将同一个 v2 签名目录扩到 17 项会让旧客户端拒绝整份目录，单纯分组也无法解决。建议为新客户端设计独立版本通道或其他可验证的兼容机制：旧客户端继续收到不超过 16 项的旧通道，新客户端使用扩容通道。两个通道的发布、序号、防回滚、签名信任、下架及单包复用策略须在实施设计中确定并验收；不能假设现有协议已经支持分页、按组拉取或客户端能力协商。不得通过裁掉用户已安装条目来规避旧客户端限制。

官方分组元数据优先作为独立、带签名的可选文档：旧客户端不读取，新客户端失败时仍可使用游戏目录。是否复用现有签名封套和信任链须审查后确定，不与游戏资源更新绑定成不可分割的整体。升级大厅才能提供新界面、100 项能力；此文档不授权或触发 APK 发布。

## 5. 分期与验收

- [ ] 阶段 A：先形成需求、交互稿和版本兼容方案，确定旧版通道及 100 项口径，审查后决定是否实施。
- [ ] 阶段 B：扩大目录能力，建立兼容通道并验证旧客户端、版本回退防护和签名；单独上线顺序由发布方案确定。
- [ ] 阶段 C：默认分组、两级展示、搜索、单游戏安装与更新，支持离线及异常状态。
- [ ] 阶段 D：自定义分组、跨组引用、排序、隐藏默认组和配置备份；验证退出重进、升级和数据恢复。
- [ ] 阶段 E：浏览器/设备适配、性能与无障碍检查，形成评审和发布证据；真机安装可由用户在发布后验收。

验收场景至少包括：同一游戏加入两个组后仅安装一份并共享存档；删除其中一个组后游戏仍能打开；更新一次后所有组显示一致；离线进入已安装游戏；未安装、更新失败、下架及空组状态；本地分组损坏/导入失败不丢原配置；旧客户端继续读旧目录；100 个动态 ID 接受、101 个拒绝；既有四款内置和动态游戏及存档不受影响。验收应覆盖手机、平板、大字体、键盘/读屏和 100 项时的性能；具体指标实施前确定。

## 6. 待讨论

默认分组的分类名称和初始归属；首页默认显示全部游戏还是分组；是否提供分组配置跨设备同步；是否允许对官方组直接个性化；更大规模时如何扩展至超过 100 项。以上均为建议，未视为用户已经确认。
