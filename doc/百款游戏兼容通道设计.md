# 100 款动态游戏兼容通道设计

状态：规划中，须提交后审阅；2026-11-01。

- 现状：生产 `game-resources-v2` Release ID 407394942 只有 `catalog.signed.json`，旧客户端硬限制 16；现有新版代码上限 100，但生产签名器仍限制 16。游戏资源按 ID 安装，签名证明、序号及哈希持久化；已有两款新游戏发布在序号 40。
- 建议：同一固定 Release 保留旧 `catalog.signed.json` 并引入独立 `catalog-expanded.signed.json`，复用现有 schema 2、生产公钥和 ZIP 资产；两份目录均独立验签、绑定同一 Release 和真实 ZIP，且旧目录永不超过 16 项。新客户端只选择扩容目录，目录不可用时保留本地可信资源并报告；不因扩容目录无效或缺失而静默降级到旧目录。
- 初次扩容目录由当前生产旧目录逐字节复制，目录序号及摘要相同，已安装旧客户端升级时不会产生等序号不同摘要的冲突；上线顺序先发布和匿名验证扩容目录，再发布新 APK。扩容目录后续签名时保持已知 ID 累积、版本不回退、序号严格增加，旧游戏和 ZIP 证明不变，禁止不同载荷复用同一序号。
- 双通道后续维护需明确旧目录保留哪些游戏、如何同步版本和续期，确保扩容目录对旧目录中同游戏不低于版本水位、相同版本哈希与描述一致；发生部分发布、超时或并发发行时有明确事务与恢复机制。旧目录永远不能超过 16，扩容目录最多 100；任一旧目录更新后必须形成可审计的同步步骤，严禁各自独立签发破坏迁移或防回退。
- 签名资源目录仍使用 schema 2 和固定 Release 身份；既有每个游戏独立资源 URL 和存储 origin 不变，版本证明仍能验旧目录签名。不能仅凭资产文件名、无签名数据或环境变量放宽策略。所有网络/签名/错误路径先验证后写入，失败保留原状态。
- 签名载荷 512 KiB、信封 1 MiB 和 GitHub API 资产分页/4 MiB 预算需基于 100 游戏模拟与真实资源目录检查，超过预算应明确拒绝且不得破坏当前可用目录。
- APK 版本/签名根据实际线上正式版核定；采用现有外置发行密钥，不将私钥提交仓库。启动提醒与资源更新流程保留。新增渠道不涉及游戏分组。

待实施前审阅并确定：双通道发布原子性和安全重试、首次/更新目录序号及并发同步、已升级用户离线与回退、防止旧 APK 读取超 16 条状态的兼容边界。不得把此草案当成已验证方案。

- 状态变更：同版本资源的 `available` 上架/退役状态允许扩容目录先行，短暂两目录不同；旧目录激活前必须与扩容目录中对应游戏的状态完全一致，其他同版本描述字段仍必须一致。这样退役和重新上架都能按扩容先、旧版后的顺序完成，避免旧目录超前。
