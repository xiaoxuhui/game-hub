# 四游戏与动态资源候选及发行手册

状态：生产工具已实现并完成独立候选验证；v0.3.0 与首份 game-resources-v1 签名目录已发行并匿名核验，见[发行记录](evidence/m7-v030-release-20261009.md)。资源发行由大厅维护者审核和签署，源仓库只有只读访问。

## 来源与编号

`sources.lock.json` 是 APK 内置四游戏的固定基线。未来子游戏资源更新修改 `resource-sources.lock.json` 中对应游戏的完整 Git SHA、源码版本和所需文件列表；仓库、ID、构建类型和入口保持当前合同。资源代码不能采用浮动分支或标签。源码 package.json 版本须与资源来源锁一致。

同步修改 `resource-releases.lock.json` 中该游戏的 sourceRevision、递增 contentCode 和发行说明。编号 1 只允许原基线，后续编号不得复用；发行回退旧代码也使用新编号。编号单调性还由签名目录和客户端可信水位验证。首次目录包含四份编号 1 的原基线，不会让现有内置游戏重复下载。

源项目发布或提交后，维护者先选定提交并审阅存储键、数据格式、原生桥、Worker、缓存和双向存档兼容性。源项目发布独立 APK 不会自动生成已签署的大厅资源。需要存档迁移或原生改动的资源不能沿当前兼容合同进入自动更新通道。

## 独立构建

将大厅对应完整提交检出到新的独立目录，保持 Git 工作树干净，不设置 GAME_HUB_LOCAL_SOURCES。在该目录执行：

```powershell
pnpm run check
pnpm run prepare:resources
pnpm run verify:resources
```

prepare:resources 从远端克隆四份完整提交，在独立克隆中执行源码构建，产物先写 `.build/resource-source-assets`，不会改 APK 内置资产；再生成 `.build/resource-candidate`。候选包含四 ZIP、games.unsigned.json 和 candidate.json。后者绑定大厅提交、APK 基线锁、资源来源锁和资源编号锁的摘要。修改锁文件后旧候选失效，必须重新构建。

工具验证入口、关卡/Worker、文件清单与哈希、ZIP 结构、许可、禁用的缓存代理及广泛清空存档调用；这些检查不能替代四游戏实际存档兼容与桥操作验收。候选应重复独立构建并比较 ZIP 哈希，归档依赖锁、构建日志、兼容测试和提交后独立审阅记录。原游戏仓库仅做前后 SHA/工作树状态读取。

可在大厅 Actions 手动运行 Prepare unsigned game resources，得到未签名候选；该工作流只有 contents:read，不创建发行、不持有任何私钥。下载候选后须复核同一源码提交和所有锁摘要。

## 签署与公开通道

当前资源协议仍为 v1；候选文件格式 v2 是维护工具的归属记录，未改变 APK 接受的签名目录协议。资源固定发行 game-resources-v1 必须是预发布，正式最新发行仍用于大厅 APK。全部 ZIP 上传且复核归属、大小、摘要后才签署并最后上传目录；保留旧目录引用的 ZIP。目录序号递增，签名覆盖原始 UTF-8 字节。

发行前需要真实候选兼容验收、提交后独立审阅和开源检查。2026-10-09 用户授权本轮 v0.3.0、v0.4.0 先发行，资源/APK 密钥的异机备份恢复延至待办，见版本待办清单；不将同机恢复冒充异机验证。维护者用仓库外的资源私钥签署，私钥不进源码、候选、APK、Actions 或公开日志。签署工具支持从标准输入读取私钥，不要求落明文文件。

公开后匿名核验签名目录、资产归属与每个 ZIP，并用旧 v0.2.0 和新大厅检查双通道。用户真机安装验收在发布后记录。第三阶段动态扩展将在第二阶段发行后单独开发并采用兼容通道，不直接放宽本版四游戏协议。

## v0.4.0 动态资源 v2（发行准备中）

另用固定预发布 `game-resources-v2`，保持原 v1 四游戏校验。`dynamic-sources.lock.json` 记录每个动态游戏的来源仓库/完整 SHA、明确文件范围、许可、入口、编号、名称、类别图标和稳定存档合同。原仓库只读，维护者在干净的独立大厅检出运行 `pnpm run prepare:dynamic`、`pnpm run verify:dynamic`，候选位于 `.build/dynamic-candidate`。生产候选逐文件与固定提交 blob 比较，并绑定完整大厅提交和来源锁摘要。

全部 ZIP 完成独立兼容测试、提交后审阅、可重复验证并上传后，才能匿名 capture 完整资产快照。通用签署入口：

```text
node scripts/dynamic-catalog.mjs capture snapshot.json
node scripts/dynamic-catalog.mjs sign payload.json - resources-20261008 catalog.signed.json snapshot.json [previous-signed.json]
node scripts/dynamic-catalog.mjs verify catalog.signed.json android/app/src/main/res/raw/resource_public_key.der resources-20261008
```

`-` 表示维护者将私钥仅通过 stdin 提供，禁止把私钥正文写入命令、日志或源码。工具不持有凭证、不创建密钥、不执行网络发布；签署前验证固定 v2 预发布归属和每个资产大小/摘要。输出不覆盖既有文件。首序号必须为1，后续必须提供同一信任根验证的已发行签名历史，递增目录序号、保留全部历史 ID，内容编号不得倒退。相同编号只允许 available 状态变化，其余描述/字节须一致；改变资源或描述应使用新编号。客户端同时保留自己更高的可信水位。

公开目录始终累计最多16个动态 ID。退役设 available=false、保留完整描述及被引用 ZIP，不删历史 ID；恢复提供相同资源须新目录序号，修改字节须新内容编号。目录最后公开，旧 ZIP 保留；更新固定目录资产的未知结果先只读查询核对，不能盲目覆盖或移动标签。正式大厅 latest 不指向资源预发布。

首份自有示范的正式生产公钥、实际公网安装以及后续局部更新仍属 N5/N6 发行验收；Node/受控设备夹具不能替代这些结果。两个用户新增游戏资源包和最终临时文件清理分别列 N7/N8。
