# N31 网页版大厅资源自动同步设计

> 状态：**方案待实施**（2026-11-23 定稿，工作量约一个工作日，肖工决定暂缓）
> 适用：`gh-pages` 网页版大厅与 APK 签名资源目录的版本一致性

## 1. 背景

大厅有两个消费端，各自维护一份游戏清单：

| | APK 通道 | 网页版通道 |
|---|---|---|
| 地址 | `catalog-expanded.signed.json` / `catalog.signed.json` | <https://xiaoxuhui.github.io/game-hub/> |
| 部署 | GitHub Release（`game-resources-v2` 等） | `gh-pages` 分支静态站点 |
| 清单 | 签名目录，发布器生成 | `games.json`，**手工维护** |
| 资源形态 | ZIP（`archiveSha256` + 逐文件 sha256） | 解包后的静态目录 `games/<id>/` |
| 更新触发 | 发布器自动，改锁即生效 | 人工复制 `dist` + 改 JSON |

网页版不在发布链路内。每次新增游戏或更新资源，只走了 APK 那条线，网页版靠人记得手动补。

## 2. 现状问题（2026-11-23 实测）

网页版 `games.json` 共 28 条（4 内置 + 24 动态），与签名目录逐条比对：

| 类型 | 数量 | 明细 |
|---|---|---|
| 版本一致 | 20 | — |
| **版本落后** | **6** | compass 1.0.0→1.1.0（cc3→4）、lambda 0.3.5→0.4.0（cc9→20）、light cc2→3、logic-circuit 0.3.54→0.3.56（cc42→44）、sokoban 1.0.0→1.0.3（cc3→6）、turing 0.6.0→0.7.0（cc4→5） |
| **完全缺失** | **2** | `territory-conquest`「疆界 · 领土争夺」v1.2.0 cc4、`cube-step-solver`「魔方一步步」v1.0.0 cc1 |

玩家侧表现为：网页版打开是旧版本，最新接入的游戏在网页版里根本找不到。

## 3. 目标与非目标

**目标**

1. 发布完成后，网页版与签名目录的 `id / version / contentCode` 自动一致，无需人工介入。
2. 清单只有一份权威来源（签名目录），`games.json` 由它派生，禁止手写。
3. 任何不一致在发布当时暴露，而不是等玩家发现。
4. 单款游戏更新时，访客只重新下载该游戏变化的文件。

**非目标**

1. 不追求两边运行时完全等价：存档容器不同（APK 私有 origin / 浏览器 localStorage），**存档不互通**，这是设计使然。
2. 不消除 MIME 白名单差异：APK 只收 js/html/css/json/svg/png/jpg/webp/txt/md，网页版无此限制。该差异保留，但会因清单统一而更早暴露。
3. 不改动 APK 侧发布流程与 v1 人工闸门。

## 4. 架构

```
游戏仓库 dist
   │
   ├─→ 发布器构建 ZIP → 签名目录（APK 消费）
   │                        │
   │                        └─→ 【新增】镜像步骤 → gh-pages/games/<id>/
   │                                              gh-pages/games.json（派生）
   │                                              gh-pages/offline-manifest.json（重算）
   └──────────────────────────────────────────────┘
```

镜像的输入不是游戏仓库，而是**发布器已经产出的候选包**，避免二次构建导致内容漂移。

## 5. 关键改造：`sw.js` 缓存策略（必做前置）

### 现状

```js
const MANIFEST_SHA='d6f4a41a…', WORKER_SHA='7f6312d4…',
      PREFIX='game-hub-offline-v1-',
      CACHE=PREFIX+MANIFEST_SHA+'-'+WORKER_SHA;
```

缓存名内嵌 manifest 摘要，`activate` 时删除所有同前缀旧缓存。**任何一次清单变化都会让全部访客重新下载全部 28 款游戏**（snake-speed 单款约 13MB）。

手工低频更新尚可接受；改成每日自动同步后，这是不可接受的流量与首屏代价。

### 改造

1. 缓存名与 manifest 摘要解耦，改用固定版本号（如 `PREFIX+'v2'`），仅在缓存结构变更时手动 bump；
2. `manifestFromNetwork()` 的 sha 校验**保留**（防篡改、防错误缓存），只是不再参与命名；
3. `prepare()` 已有“校验既有缓存 → 只补缺失/变化文件”的逻辑，解耦后增量自动生效，无需重写；
4. 新增清理：`prepare()` 完成后删除缓存中不在本次 manifest 内的条目，避免不可达文件长期占用；
5. `offline-inspect` 的返回结构保持不变，`offline-ui.js` 无需改动。

### 验证要求

这部分必须用真实浏览器验证，不能只跑单元测试：

- 首次安装：全量缓存完成，离线可开；
- 单游戏更新后：只重新拉取该游戏变化的文件（比对 Network 面板）；
- 下架/重命名文件：旧条目被清理，不残留；
- 离线状态下打开：首页与已缓存游戏均可运行。

## 6. 镜像脚本设计

新增 `scripts/publish-web-hub.mjs`。

### 输入

| 来源 | 用途 |
|---|---|
| `.build/dynamic-candidate/`（`dynamic-resources.mjs` 产物） | ZIP 与 `games.unsigned.json`，避免二次构建 |
| `dynamic-sources.lock.json` | `files` 清单（决定复制哪些文件）、`contentCode`、`entryPage` |
| 已发布的 expanded 目录 | 增量比对基准 |
| `gh-pages` 工作树 | 写入目标 |

### 步骤

1. **挂载工作树**：`git worktree add` 到 `<工作区>/work/gh-pages-<日期>`，不污染主检出；
2. **增量判定**：读 gh-pages 现有 `games.json`，逐款比较 `contentCode`；相同则跳过，仅处理变化或新增项；
3. **复制文件**：按 lock 的 `files` 逐项复制（先清空目标 `games/<id>/`，避免删文件后留残骸），保证与 APK 包**逐字节一致**；
4. **派生清单**：全量重写 `games.json`，字段为 `{id, name, version, contentCode, entry}`，取自签名目录，**不读手工值**；
5. **重算离线清单**：遍历工作树全部文件生成 `{path, bytes, sha256}`，`baseline` 更新为本次 gh-pages 提交；
6. **提交推送**：单条提交，message 形如 `web-mirror: seq <N> <摘要>`；不混其他改动。

### 不变量

- `games.json` 的条目集合必须等于（v1 4 款 ∪ expanded 26 款）；
- 每款 `files` 的复制结果 sha256 必须等于签名目录内的对应值；
- 任一步校验失败即整轮放弃，不推半成品。

## 7. v1 四款的处理（待决策）

网页版的 conway / eml / light / turing 来自 v1 目录，而 v1 有**人工闸门**（内置款误加/误删 id 会让存量 APK 整份拒绝目录）。三种做法：

| 方案 | 做法 | 代价 |
|---|---|---|
| A（推荐） | 严格镜像 v1 目录，与 APK 完全对齐 | v1 不发则网页版不同步（当前 turing 卡在 0.6.0） |
| B | 跟游戏仓库 `dist` 最新 | 网页版会比 APK 新，版本差成为常态，更难解释 |
| C | 4 款继续手工，脚本只管 expanded 24 款 | 最少改动，但内置款仍是人工盲区 |

方案 A 与“一致性优先”的目标相符，代价是 turing 的适配器问题解决前，网页版这 4 款会滞后——这是真实约束，不是同步失败。

> 补充（2026-11-23）：另见 `doc/N32-内置款并入动态通道设计.md`。若四款将来并入 expanded 动态通道，本节的三选一会自动收敛为一种——网页版只需镜像 expanded，不再区分内置与动态。两件事有先后依赖：本节先定，N32 再动手。

## 8. 护栏

| 护栏 | 内容 |
|---|---|
| 快照 | 推送前给当前 gh-pages HEAD 打 tag `web-snapshot-<日期>-seq<NN>`，可一键回滚 |
| 冒烟 | 本地起静态服务，加载首页 + 抽 3 个变化游戏，确认 `index.html` 200 且无 pageerror，再推 |
| 失败即停 | 下载、校验、解包、manifest、冒烟任一失败，整轮放弃，线上保持上一版 |
| 告警 | 对齐校验（`games.json` vs 签名目录）不一致时报告，不静默通过 |

## 9. 实施顺序

1. `sw.js` 缓存改造 + 真实浏览器离线回归（独立、可回滚、不碰发布流程）；
2. 镜像脚本 + 手动跑一次补齐现有 8 个差异，观察线上；
3. 接入每日任务（发布核验通过后调用），并启用对齐校验告警。

顺序不可颠倒：若先上自动化再修缓存，两类故障会混在一起，排查成本极高。

## 10. 验收标准

- [ ] 网页版 `games.json` 与签名目录的 `id/version/contentCode` 三元组完全一致；
- [ ] 单款游戏更新后，网页版访客只重新下载该游戏的差异文件；
- [ ] 离线模式下首页与已缓存游戏可正常启动；
- [ ] 镜像失败时线上保持前一版本，且有明确报告；
- [ ] 对齐校验在人为制造不一致时能报警。
