# 双形态能力对等矩阵（APK × 网页版）

- 日期：2026-10-21
- 前提：**游戏大厅必须同时提供 APK 与网页版，两者同级**——网页版用于解决非 Android 设备可用，不是 APK 的替代品
- 定位：W0 的前置产物。回答一个问题——**"同级"具体同到什么程度**，逐项列清差异，不靠口头约定
- 关系：本表是 W01–W17 十七项门禁的**能力侧索引**，不是它们的副本

## 使用规则（防漂移）

1. **不复制通过条件**。W01–W17 的场景与通过条件真源是[设计第 9 节](跨平台网页版游戏大厅设计.md)，[需求与测试用例](网页版大厅需求与测试用例.md)第 45 行已明确禁止复制成第二份清单。本表只记「对等态 + 挂靠编号 + 依据」。
2. **改对等态必须同步改挂靠的 W 用例**，或在该用例里写明"为何不由此表驱动"。只改表不改用例，等于表作废。
3. **W1/W2 报告里每一个"降级"都必须写出差异说明**，不得直接写"通过"。W1 的 DoD 要求"未支持能力明确不可用，不冒充全覆盖"——本表就是判断依据。
4. 新增能力或新游戏接入时，先在本表加行，再写 W 用例。

## 对等态三值定义

| 值 | 含义 | 验收要求 |
|---|---|---|
| **等价** | 两端行为与验收条件相同 | 同一用例两端各跑一次，结果一致 |
| **降级** | 能力存在，但实现方式或边界不同 | 必须写明差异点，并在 W 用例中分别断言 |
| **不可用** | Web 端无对应能力 | 要么做适配层，要么在 UI 明确告知用户不可用 |

## 两个硬缺口

### 缺口一：namespace 解决不了换域名

Web 端存档 namespace 已定为 `game-hub/<gameId>`，**不带域名、不带 basePath**。它能覆盖的范围要说清：

- ✅ 覆盖：同一个 origin 内的变化 —— basePath 由 `/` 改为 `/hub/`、页面路径调整、游戏版本升级
- ❌ 不覆盖：**换域名**。IndexedDB 与 localStorage 按 origin 硬隔离，换域即换 origin，旧档根本读不到，与 key 叫什么无关

因此换域名的唯一可靠迁移路径是**显式导出 / 导入**（#5 能力项）或一次性同源搬运脚本。这正是 W11「域名迁移预演」用例存在的理由，也意味着 **W4 域名冻结后若再变更，必须预留迁移窗口**，不能当作配置项改一改。

### 缺口二：Web 端没有原生桥

`#10` 是唯一被判定"不可用"的运行时能力，且它不是可选项：

- APK 侧每个游戏都挂一个专属桥：`addJavascriptInterface(SaveBridge(), bridgeName(game.id))`，导出走 `exportBridgeJs`；
- 游戏侧对桥的调用点分散且深度不一，已核到的位置包括 `light_game/scripts/storage.js`、`abelian-sandpile/src/app.js`、`lambda-diagram-game/src/download.js`、`logic-circuit/src/app.js`，另有同名桥测试在 `*/tests/android-shell.test.js`；
- 结论：**Web 端适配层是必做项，且必须逐游戏核对依赖深度**，不能用"统一替换一个 download 函数"带过。若某游戏强依赖桥的同步返回（`saveFile():Boolean`），Web 端需明确降级语义（例如改为异步下载 + 结果提示），这属于"降级"而非"等价"，须在 W14 记录。

## 与 N25 的关系

本表的 #4 / #5 / #15 三项即 L1 存档兼容矩阵的 Web 侧输入；#10 决定 N25 的 L0 是否要包含"桥抽象"。在 L0 做薄的前提下（消费方仅 game-hub 一家），**桥抽象放 L1 还是 L0 由 #10 的适配层形态决定**，建议等 W1 实测后再定，不要在 W0 之前先写抽象。
