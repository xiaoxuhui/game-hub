# N13 全仓每日巡检与发行设计

- 状态：设计完成，部署按[实施计划](N13-全仓每日巡检实施计划.md)逐阶段验证。
- 需求：[全仓需求](N13-全仓每日巡检与发行需求.md)。

## 每仓自检，共用实现

八仓库各放一个 schedule + workflow_dispatch 包装工作流，调用大厅公开仓库中固定完整 SHA 的 reusable workflow。包装工作流以自己的 GITHUB_TOKEN 查询自己的默认分支、正式版本、标签真实提交和差异；公共代码在调用者作业上下文执行，仍能访问 github.token，因此固定SHA及独立审阅是信任边界。caller权限限定contents:read，禁止secrets:inherit；actions/checkout设persist-credentials:false，不将令牌保存在Git配置中。被调用代码可使用调用仓只读令牌查询私有仓，不能宣称该代码与令牌隔离。mini-app-harness 的报告只保存于它自己的私有 Actions artifact。大厅仍用原六源检测已发行资源的固定基线。

GITHUB_TOKEN 权限限于所在仓库，不需要为八仓检测创建跨仓写令牌。源码/资源消费者的只读边界保持。依据：[GitHub token 权限](https://docs.github.com/en/actions/concepts/security/github_token)、[复用工作流](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows)。按追加要求改为每日北京时间06:00（UTC22:00）统一启动，后续自动候选/发行从同一巡检结果继续；GitHub schedule 可能延迟或丢弃，公开仓库长期无活动会禁用，失败需关注 GitHub 通知。[schedule 依据](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)。

读取正式 latest（资源通道为预发布，不混作正式 APK），解析 git/ref/tags 再按最多四层 annotated tag 解析 git/tags；要求最终 commit 完整 SHA。主分支与已发行 SHA 相同/领先/落后/分叉分别记录，≥300 文件视为截断，不能放行。只读检测分类不等于发布批准，CI/测试变动在自身发布中仍属于候选变动。请求超时20秒，任务10分钟，报告始终上传30天，单仓互斥，仓库之间不互相取消。

没有正式发布时明确 no-release，输出主分支 SHA；没有初始版本合同就不自动首次发布。无修改时不发版本；改文档/测试本身不自动增加 APK。私有仓库仅当自身工作流运行时读 API，不把私有 SHA/差异带进公共汇总。

## 全仓自动发布目标（后续实施）

按用户追加发行策略：每日默认只检查并构建Actions候选，兼容资源未来追加现有签名通道，正式APK/独立游戏版本按阶段集中发行，不每天新建Release。具体边界见[自动检查与发行策略](自动检查与发行策略.md)。

| 仓库 | 交付物 | 候选门禁与发布位置 |
| --- | --- | --- |
| game-hub | 正式同证书 APK、v1/v2 累计签名资源目录 | 当前资源/Android 门禁及升级烟测；大厅 Release |
| 六个子游戏 | 自身网页版及同证书 APK；供大厅消费的资源候选 | 各游戏领域/浏览器/存档测试，自身 Release；大厅只读固定 SHA 再适配打包 |
| mini-app-harness | 版本化技能源归档 | 技能严格校验、引用/许可门禁；私有版本交付，不生成 APK |

统一流程：检测 → 固定 source SHA → 隔离候选 → 领域/交互/双向存档读取及扩展保护门禁 → 版本/证书/双构建核验 → 自动审阅与批改留痕 → 签名 → 幂等发行 → 公网/私有授权下载验收。人类真机补验可在发行后，不阻塞可重复的自动检查。不能依靠 cron 执行大模型代码改写来代替确定性的构建和门禁。

每仓维护 release-policy 合同，明确发布模式、构建适配器、输出白名单、版本与 lastPublishedSource、证书摘要、门禁报告及兼容策略。先接入候选，再启用自动发行。状态包括 unchanged、candidate、blocked、failed、published，失败不可冒充最新；未知依赖/schema/capability 必须 blocked 并保留报告。适配器/发布权限只作用于自身仓库；大厅无子游戏源码写权限。

自身发布 job 才申请 contents:write。用 GITHUB_TOKEN 推标签通常不会触发另一个 push 工作流，因此在同一 DAG 显式调用构建/发行，或显式 workflow_dispatch，不依赖隐式事件。[官方事件规则](https://docs.github.com/en/actions/concepts/security/github_token)。禁止强推/移动正式标签；(仓库, source SHA, artifact kind, version) 为幂等键，同版本同摘要重试可恢复，不同摘要停止。ZIP 全部上传并验证后才发布签名累计目录；旧 ZIP/目录历史不可删除。目录 sequence/contentCode 与用户端反重放水位持续递增。

大厅正式私钥目前为本机 DPAPI，Linux runner 不能解密。后续采用受控隔离签名服务或专用可信 Windows 签名执行端，仅收已核验候选与摘要，不运行未经审阅的上游任意脚本；公网上传权限与构建/签名权限分离。不能把现有本机令牌/DPAPI 文件复制进 Actions 作为方案。六游戏已发布 APK 的证书必须逐个核对，维持固定签名（含历史固定 debug 证书），禁止自动换钥。新增云端 App/签名服务的注册或密钥托管须有具体配置再部署。

自动化开关在发布合同、存档能力、签名服务未验证前保持关闭；本轮每日报告写明 release-contract-not-configured。不宣称所有仓库已自动发行。三游戏迁移按照[兼容规范](存档格式与升级兼容规范.md)接入之后再恢复资源发行。
